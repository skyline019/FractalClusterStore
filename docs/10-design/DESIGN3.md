# XDB v3（FCS）设计 —— 平衡不是树，而是四个正交的旋钮

> 一句话：**树只是"平衡"的一种表现形式。** 真正的平衡是把"有序、分层、局部性、
> 回收"这四个维度交给四个互不干扰的旋钮去调，再让每一层都长得像同一张脸。

v1/v2 用的是 B+ 树：一种把"平衡"硬编码成"节点半满"的结构。它的代价是每次写入都要
原地改页、分裂、下沉——写放大 19~56×。v3 换掉了这个前提：

| | v2（B+ 树） | v3（FCS，单次提交落盘） | v3（组提交，8:1） |
|---|---|---|---|
| 写放大（20000/500） | 22.5× | **3.17×** | **1.69×** |
| 写放大（200000/2000） | — | **3.99×** | **2.45×** |
| 读放大 | 每层一次页读 | **0.11~0.68 次 run 探测/get**（布隆门控） | 同左 |
| 空间放大 | — | **1.04~1.31×**（小值）；大值见 §10.8（1.0~1.5×，取决于是否对齐 4080） | 同左 |
| 点查 | — | 比 SQLite 快 **2×** | |
| 覆盖写 | — | 比 SQLite 快 **2.5×** | |
| 区间扫描（100 行） | — | 比 SQLite 慢 **4.5×** | |

> 上表是 v3 定型时的快照（组提交 8:1 用的是 20000/500 那一组）。**当前代码的实测矩阵在 §10.1**：
> 20000/100 **3.63×**、20000/500 **2.70×**、50000/1000 **2.35×**、200000/2000 **2.77×**、
> 200000/2000 + 8:1 组提交 **2.23×**，与上一版逐位相同（§13.5 只说能力扩展，不动热路径）。

## 1. 三层同构：store → cell → run → page

```
store  ─┬─ cell[0, k1)  ─┬─ seg(run 7, 页 12..14, 键域 [0, k1))    ← 最新
        │                 ├─ seg(run 9, 页 31..32, 键域 [0, k1))
        │                 └─ seg(run 3, 页 88..89, 键域 [0, k1))    ← 最旧
        ├─ cell[k1, k2) ── ...
        └─ cell[k2, ∞)  ── ...
```

每一个层级都是同一张脸：**一段按键序排列的东西 + 一层把它们分成"段"的索引**。

| 层 | 有序序列 | 分层方式 | 定位手段 |
|---|---|---|---|
| run（磁盘） | 记录 | 页（4 KB） | 每页 fence + 稀疏记录索引 |
| cell（内存目录） | 段 | 键区间 | `std::map<u64,Cell*>` 二分 |
| 段 | 页 | 页区间 | 段自带 `(klo,khi)` 键域 |
| 页 | 记录 | — | 页内顺序 + 每 16 条稀疏项 |

递归带来的是**同一段代码在四层上复用**：`merge_emit` 只认"若干有序游标 + 一个键域"，
于是它同时是：读路径的 k 路归并、压实、分层合并、以及外部的范围游标。

## 2. 段的键域（klo,khi）：让"页共享"变得安全

一次提交写出的 run 覆盖整个键空间，于是它的**边界页必然跨 cell**。早期版本给每个 cell
一段 `[p0,p1)` 页区间，边界页被两个 cell 同时计入、两份记录同时可见——空间虚高、
合并时重复计入。

v3 给段加键域：**每个段只为自己那一截键负责**。页里的邻居记录既不计入本 cell 的存活账，
也不会被本 cell 的归并读到。

这一个字段带来了三个连锁好处：

1. **切分零搬移**：把 cell 在 k 处切开，只是把两个子 cell 的段键域收窄；
2. **页可以共享**：一个 4 KB 页被相邻 cell 共用完全合法，不需要重新写；
3. **账目可精确**：`live = Σ(最新副本字节)`、`dead = Σ(页内记录) − live`，逐字节对得上。

## 3. 读：布隆门控 + 新→旧扫描 ⇒ 读代价 ≈ 1 页 + ε·段数

```
get(k):
  ① 目录二分 → 找到 k 所在的 cell            O(log #cell)，内存
  ② 段按 seq 从新到旧遍历                    每段一次 Bloom 位测试（内存）
  ③ Bloom 说"可能在" → 用段键域裁剪 → 页 fence 二分 → 页内稀疏索引 → 顺序找到记录
  ④ 第一个命中即最新版本；命中 tombstone ⇒ NOTFOUND
```

关键点：**Bloom 说"不在"的段一个字节都不用读**。每键 16 bit、4 个探测位，误判率 ≈ 0.24%，
于是"段数很多"只影响 CPU（一次位测试 ≈ 2 ns），不影响页读。

实测（bench3，23~25 条 run）：

```
probes/get = 0.65 ~ 0.68      # 即"平均只碰 0.68 个 run"
页读/get  ≈ 1.05 ~ 1.15
```

这就是**敢把 `SMAX` 放大到 512 的底气**：读放大不再随 run 数线性增长。反过来，这也让
"为了少而合并"的写代价变成了纯粹的可选项。

### 3.1 游标（Cursor）

范围访问不是"把整条流拼出来"，而是**可暂停、可重定位**的状态机：

```cpp
Store::Cursor cur;
cur.open(&s, lo, hi, view);              // view=0 ⇒ 当前打开版本
while (cur.next(k, v, len)) { ... }      // 中间可以任意插入 get/put/commit
cur.seek(k2);                            // 重定位（分页、二次查询复用）
```

- 每个段一个子游标，跨 cell 自动续接；next() 之间可以穿插别的读写；
- **胜者规则只有一条**：可见版本最大者胜，同版本取 seq 新者胜。段在 cell 里的排列
  只是"归属"，不隐含新旧——否则合并产物（低 seq、高版本）会被读成旧值；
- `view` 支持**时间旅行**：读某个快照版本时的最新可见记录（MVCC 与查询共用一条路径）；
- 记录版本存在 run 上（见 §4），游标按 run 的 `ver` 过滤；
- 输出值指向内部缓冲，有效到下一次 `next()` —— 零拷贝，但语义明确。

上层的三种查询都是它的薄壳：

| API | 语义 | 复杂度 |
|---|---|---|
| `select(lo,hi,fn,limit,offset)` | 区间扫描 + 分页 | O(k 段 × 命中页) |
| `select_at(view,...)` | 快照视图扫描 | 同上 |
| `select_prefix(pfx,bits,fn)` | 前缀扫描（高 bits 位相同） | 同上 |
| `index_scan(idx,slo,shi,fn)` | 二级索引区间扫描 | 同上 + 回表 |

### 3.2.1 页内定位：稀疏块二分（`probe` 不再从页首线性扫）

`sp` 里每 `SP=16` 条记录存一个锚点 `(首键, 块内末键, 页号<<16 | 页内偏移)`。

一次点查的定位是三级二分：

1. `cell.segs` 从新到旧（版本倒序）；
2. `run.fences` 找到键可能落在的那一页；
3. 该页的锚点二分到「≤ key 的最后一个块」，从那个偏移开始最多解码 16 条。

第 3 步以前是从页首线性扫到 `used`：4 KB 页放 ~200 条记录，平均要走 100 条。
`probe_prev`（每次提交、每个被覆盖的键都要走一次）也是同一条路径，所以这项改动
同时吃到了写路径的红利。

**微基准**（`/tmp/probe2.cpp`：200000 条记录、4096 个热键 × 40 轮，工作集常驻缓存，
纯 CPU 口径，避开设备差异）：

| 页内定位 | ns / get |
|---|---|
| 页首线性扫（旧） | 830 ~ 950 |
| 锚点二分（新） | **296 ~ 370** |

约 **3×**。注意它只降低“命中之后的解码步数”，不改变读页次数 —— 所以 bench3 的
`read_ops` 基本不动（这是对的：该指标的瓶颈在页缓存，不在页内）。

### 3.2 二级索引：命名空间，而不是新机制

索引键 = `1‖idx(7bit)‖skey(56bit)`，索引值 = 主键(8 B)。于是：

- 索引条目与主记录**活在同一个 store、同一次提交里** ⇒ 索引维护天然原子；
- 索引扫描 = 一次区间扫描 + N 次主键回表（回表走 Bloom 门控点查，≈1 页）；
- 用户键空间（最高位 0）与索引空间（最高位 1）在键域上天然分开，
  `select(0, IDX_BASE)` 永远不会看见索引条目。

### 3.3 区间扫描：把 k 段归并压成 k≈2

窄区间扫描的代价 ≈ 参与归并的段数 k（每段一次页定位 + 一次页解码）。三件事把 k 压下来：

1. **run 级键域摘要 `Run::sp`**（纯 RAM，每 16 条记录一块）：块内存 `(首键, 末键)`，
   二分 + 块内判断 ⇒ `run_may_have(run, lo, hi)` 用 O(log 块数) 判断"这条 run 里有没有
   落在 [lo,hi) 的键"。它是**精确**的（不是 Bloom），所以跳过永不漏行。
2. **精确键索引 `Run::kidx`（可选）**：每键 8 B 的键数组，二分直接落到页号；
   `set_key_index(true)` 打开。代价 8 B/键 RAM，换来窄区间一次定位。
3. **分层合并 + 归一**（§5.3、§5.5）：run 数从 25 降到 1~2，这是最根本的一条。

两个体温计：`sp_skips/scan`（一次扫描里整条被跳过的 run 数）与 `cursors/scan`
（真正打开的子游标数）。50k 键、窄扫 100 行：从 25.3 个游标降到 **1.98**，
扫描从 9.3 µs 降到 **0.95 µs**（同期 SQLite 1.9~3.0 µs）。

> 为什么不再加一层"64 bit 前缀指纹"：对均匀分布的键，56 bit 键空间里任意窄区间都会
> 命中全部前缀桶，前缀位图恒为"全 1"，一分钱也省不下；对聚簇键，`sp` 已经是精确的
> 键域，比位图更细。真正的一级过滤由 run 级 Bloom（点查）+ `sp`（区间）承担，
> 再加第三层只会多一份要维护的不变量。

## 4. 写：一次提交 = 一条 run

提交 = 内存表（有序 map）→ 一条追加写的 run（页内有序、页间 fence、带 Bloom + 稀疏索引）
→ 清单增量 → 超级块提交字。

- 没有原地更新，没有分裂下沉；**写路径上没有读**（除了标记旧副本为垃圾的那一次探针）。
- 一次提交写 `ceil(记录字节/4KB)` 页，顺序写，不重写；
- 只写"用到的字节"（4 B 对齐），**页尾不产生写放大**。

### 4.1 记录头：16 B → 10 B

| 字段 | v3 早期 | 现在 |
|---|---|---|
| key | 8 B | **8 - pfx B**（页内前缀压缩，见 §4.2） |
| ver | 4 B | **0**（挪到 run 上：一条 run 一个版本） |
| len | 2 B | 2 B |
| chk | 2 B | **0**（页 CRC 已经覆盖整个 `[12,used)`） |
| 合计（8 B 值，随机键） | 24 B | **18 B** |

`rec_size(len) = 10 + ((len+1) & ~1)`，即 2 B 对齐。16~24 B 的小值场景写放大直接下降
30~35%。代价是**记录级完整性只剩页 CRC**：单条记录被撕裂只能靠整页校验发现。这是显式的
交易——页级 CRC + 提交点 CRC 已经覆盖了"掉电撕裂"的全部实际形态（见 §13 f3）。

### 4.2 页内前缀压缩：有序键省 4~6 B/条，随机键一个字节都不亏

同一页上的键是有序的，所以它们的**高位字节天然相同**：一页 100 条时间戳键，前 6 个字节
（≈ 到 256 TB 键空间）完全一样。页头第 36 字节记这个公共前缀长度 `pfx`（0~7），记录只存
低 `8-pfx` 字节：

```
记录 = [键后缀 8-pfx B][len 2B][值]          页头 36=pfx  37=格式位(1)
键   = 页首键的高 pfx 字节 ‖ 本记录的后缀
```

关键设计点：

| 问题 | 做法 |
|---|---|
| 前缀必须是**页级常量**（解码时整页共用） | 封页时取 `pfx = 首键 ^ 末键` 的前导零字节数 |
| 前缀会随页内键的推进而变短 | `add()` 用**同一条公式**精确判满：`40 + n*10 + Σ(len取偶) - n*pfx ≤ 4096`，收下就保证装得下 |
| 记录要先进暂存区（压缩后才能定位） | `RunWriter` 用 6 页的未压缩暂存区，封页时一次压进页缓冲 |
| 老库怎么办 | 老页的 36/37 字节是 0（页缓冲零初始化）⇒ `pfx=0`、`fmt=0` ⇒ 走原路径，`pg_rec_size(0,len) == rec_size(len)` **逐字节相同**。**不需要格式版本号，也不需要迁移** |
| 随机键会不会更差 | 不会。随机 63 bit 键页内前导字节几乎必然不同 ⇒ `pfx=0`，页数、字节数与压缩前完全一致 |

实测（40000 条 × 32 B 值，`tests/p1.cpp`）：

| 键型 | 页数 | 压缩页 | pfx 范围 | 每记录字节 |
|---|---|---|---|---|
| 时间戳型（`t + 7i`） | **358** | 358 | 5~6 | **36.0 B** |
| 均匀随机 63 bit | 411 | 287 | 0~1 | 41.3 B |

有序键省 **12.9% 页、14% 字节**；换到带键索引的 50000 条 bench4 场景是 41.9 → 37.4 B/条
（文件 2.10 MB → 1.87 MB）。**随机键零回归**。

## 5. 回收的四条路子（按性价比排序）

### 5.1 零写回收：整条 run 全死 ⇒ 直接摘链（`retire_dead_runs`）

每条 run 维护 `live_recs / live_bytes`：写新副本时把被覆盖的旧副本所在 run 的计数减一。
**计数归零 ⇒ 这条 run 里没有任何记录还是"最新副本" ⇒ 一个字节都不用写，直接释放页。**

热点/覆盖型负载的垃圾天然成整条 run，这条路径几乎包办了全部回收：

- 某热点负载在实现该路径前是 **space_amp 9.4× / 21.4×**；
- 实现后同一负载 **1.45~1.82×**，且压实写量下降了 60%。

**快照与回收（本轮改）**：以前只要 `nsnap_ > 0`，回收/压实/合并就**整体停摆**（怕删掉
老快照还需要的版本）。现在改成"按版本筛"：

- 一条 run 只有在 `ver <= V` 时才可能被回收（更年轻的 run 里没有老版本）；
- 一个 cell 只有在"含老版本记录"时才跳过（`cell_has_old(c, vmin)`），否则照常压实；
- 归并时快照可见的版本照样保留，只是不再整体冻结。

**`V` 必须是 `snap_max()`，不是 `snap_min()`。** 快照视图的语义是"看 `ver <= 快照版本` 的
全部版本"，所以"老快照还要读的版本"是**最年轻**那个快照的版本：`V = max(所有活快照)`。
写成 `min` 会把 `(snap_min, snap_max]` 之间的版本当成垃圾——实测 `tests/s4` 里
`B`（gen1，比 `A` 新）视图 **2000/2000 全错**。方向错得很隐蔽：只看"有快照 ⇒ 更保守"的
直觉会把人带到 `min`。

效果（`tests/s3.cpp`：3000 键 × 30 轮覆盖，快照全程存活）：`used` 44 → 74 页，
**1.7×**（上一版的 `deferred_` 版本是 44 → 620，14.1×）。老快照逐键读 0 错、当前视图 0 错。

> `free_pages()` 仍然区分两种页：**run 的数据页/链**在 `nsnap_>0` 时进 `deferred_`
> （页号复用会破坏老快照的读路径）；**从未被任何快照引用过的空闲块**（`run_page_safe()`
> 判定）可以立刻复用。这条区分就是 14.1× → 1.7× 的全部来源。

### 5.2 整流压实：只有"整个 cell 重写"才能回收

一条 run 里 90% 是垃圾、10% 是活记录时，只有把这 10% 搬走，页才能释放。
而**只有当同一个键的新旧副本同时出现在合并输入里，旧副本才会被丢弃**——
这就是"回收单元必须是整个 cell"的原因（早期按"最旧几个段"做前缀合并，14 KB 重写只
回收 1 KB，就是因为新旧副本从不在同一批里相遇）。

压实的经济学被写成一个 0/1 背包：

```
成本 = live/PAGE + 1 页          （输出只含活记录 ⇒ 成本 ≈ 活字节）
收益 = dead − live               （净回收）
门槛 = dead ≥ FCS_GC_RATIO × live  （默认 2：写 1 字节必须换回 2 字节）
预算 = 2×(本次提交新增垃圾/页) + 4 ，上限 64 页   （随垃圾产生速率自适应）
```

DP 在预算内挑"净收益最大"的 cell 子集，逐个整流重写。

### 5.3 分层合并（leveled / tiered）：用可选的写换读

整流压实按 **cell** 为单位；分层合并按 **run** 为单位，解决的是另一个问题：
run 数（= 一次区间扫描要读多少页）。

```
每层最多 LVL_T=8 条 run，超了就把最旧的一组整体合并成一条、升一层（最多 4 层）。
但**只有在合并能换回东西时才付这笔写代价**：
   (a) 这一组里垃圾占比 ≥ 20%  ⇒ 合并立刻回收空间；
   (b) 或者该层 run 数 ≥ 4×LVL_T ⇒ 为了区间扫描的读放大，批量合并一次。
```

两个关键实现约束：

- **层合并产物必须继承"源里最新的那个 seq"**，不能随便塞到栈底。否则它会看起来比那些
  没参与合并、但其实更旧的 run 还旧，旧值就复活了（这个 bug 曾经让 2000 个已删键复活）。
  第 10 轮补上了它的充分条件：**合并组在全库 seq 顺序上必须连续**（组外不能有 seq 落在组内区间里的 run），
  `level_pass` 显式检查、夹缝处截断、被隔开的最老 run 提升一层（§12 坑 91）。
- **单元压实产物则相反：取新鲜 seq（全局最大）、进 L0**。单元的段集合覆盖本单元所有键的全部已提交版本，
  产物里每个版本都是此刻最新的，标成最新 run 名副其实；沿用最新源的 seq 会和还活着的源撞号、
  再经一次层合并就读到过期值（§12 坑 90，第 10 轮修）。
- **源 run 的存活账不要递减**（它们随后整条删除）。递减会把"已被更新副本覆盖"的记录
  也减掉，让还活着的 tombstone 被误判成垃圾、整条 run 被零写回收掉。

实测效果（bench3）：run 数 60~100 → **5~25**，区间扫描快 6×（53 µs → 8.7 µs / 100 行）。

### 5.4 段数安全阀

`SMAX`（默认 512）现在是纯粹的内存/CPU 安全阀。因为 §3 的 Bloom 门控，段数本身不再
伤害点查，所以这个阀几乎不触发。

### 5.5 归一 `consolidate()`：一次线性重写换"最少段、最省空间"

把**全部** run 合成一条（`merge_run_set(all, lvl=0)`）：

- 段数 → 1：区间扫描 0.95 → 0.52 µs，点查 0.44 → 0.34 µs；
- 垃圾一次性消失：`live_pages` 3.09 → **2.13 MB**（50k × 32 B；SQLite 同负载 2.35 MB）；
- 有快照时返回 `RC::BUSY`（归一必然丢旧版本，和压实同样的约束）。

定位：**批量导入末尾 / 离线检查点**调一次，不要放进提交路径——它就是一次全量重写
（50k 记录 16~75 ms，取决于缓存温度）。

### 5.6 空间归还：`shrink()` / `relocate()` / `checkpoint()`

前面五条管的是"再写的时候别浪费"，这一条管的是"已经浪费的怎么还回去"。
文件高水位（`tail_`）只涨不落，所以要三步：

1. `consolidate(0)` —— 全库合成一条 run，垃圾一次性消失（§5.5）；
2. `relocate()` —— 把这条 run 重写到**最低**的空闲整块。约束：只在"存在更低的空闲整块"时
   才搬（否则白写一遍还可能把活区抬高）；新副本写在当前清单**不引用**的页上，旧 run 到
   提交点才释放 ⇒ 搬家中途崩溃也不会破坏旧态；
3. `checkpoint()` —— 清单链也重写成一份紧凑快照。清单页很会飘到高处，不收拾它，
   尾部回落会被几页清单卡住（实测就是这样卡在 1407 页）；
4. `shrink()` —— 高水位收到"最高引用页"，`ftruncate` 文件；设备不支持收缩（NOR）时
   只收紧分配器，数据不受影响。

`compact_file()` 把四步串起来。空页密度不用单独统计：`live_top()` 就是密度为零的那一段的起点。

### 5.7 空间上限、预留与"删得掉"

设备是有限资源，所以分配器有三条硬规矩：

1. **逻辑容量取设备上限**（`cap_ = dev->max_pages`），物理长度单独记（`dev_pages_`）。
   `shrink()` 把文件截短之后，下一次写入会用 `truncate()` 把设备**再长回来**。
   旧实现里 `truncate()` 只允许收缩 ⇒ `shrink()` 变成一次性的永久封顶，库会在某天
   突然永久 `NOSPACE`。这条现在有测试守着（`r2` 阶段 1：压实收缩后再写 126 条）。
2. **给维护留 1/8**：用户写入的上限是 `cap − cap/8 − 2`，压缩/合并/清单页可以动用
   整块容量。否则"库满了"和"库没法压实"会同时发生 —— 死锁。
3. **不增长的批可以透支预留区**：一批写如果全是覆盖/删除（新字节 ≤ 被替换字节），
   它不会让存活集变大，因此允许动预留区。这条保证 **`del()` 永远能提交**，
   于是 `NOSPACE` 永远有出路：删数据 → 压实 → 继续写。

维护是**尽力而为**的：`compact_pass` / `level_pass` 拿不到空间就跳过本轮，
绝不让用户提交跟着失败。`NOSPACE` 只由"真的写不下"产生。

### 5.8 存活账：前缀和 + 单选段快路径

`recount(c)` 是存活账的唯一算术入口，原来一次要做两件重活：
一遍 k 路归并算 `live`，再一遍**逐条解码**算 `total`（`total_rec_bytes`）。

两个观察把它砍掉了大半：

* **页里的记录字节数就是 `pbytes[i] = used - DHDR`**（封页时已经算好，`verify` 还交叉校验）。
  于是「本单元的这些页里一共有多少字节」= 整页区间走前缀和 `pcum`，只有被单元键域切断的
  那一两页需要真去解码。这一步与段长无关，O(1)。
* **单选段单元根本不需要归并**：单元里只有一份副本 ⇒ 没有谁能覆盖谁 ⇒ `live = total`、
  `dead = 0`、`live_recs = 该键域内的记录数`。记录数用每页记录数的前缀和 `pncum` 同样 O(1)。
  挂载时这种单元占 **462/499（92%）**。

多段单元仍然老老实实做精确归并 —— 那是「存活账精确」这条不变量的锚点，不能拿近似换。

`s2` 长跑（40000 op，每 4k 次记墙钟）：末段 **246.6 ms → ~110 ms**，漂移比 3.49× → **1.53×**。
bench3 的 200000/2000 耗时 0.372 s → **0.333 s**。

## 6. 快照与回收的互斥

MVCC 快照要求"旧版本仍可读"，而压实只保留最新版本。因此：

- `nsnap_ > 0` 时 **暂停一切回收**（压实的记录会写进 `pending_free_`/`deferred_`，
  提交点落盘后才真正回到空闲表）；
- 回退（rollback）是 O(1)：恢复 `{vers, tail, man_last, nman, man_first, pend}` 指针
  以及两张"尚未归位"的表（`pending_free`、`deferred`），重建目录，**不重写任何数据页**；
- 回退是**持久**的：版本时钟只前进不后退（`vers = 回退前的时钟 + 1`），否则另一个
  超级块槽里"版本更高的旧分支"会在下次挂载时胜出，把回退整条复活（§12 之 32）。

## 7. 持久化：提交点内联，清单只做大块

每次提交只写**一页超级块**，把本次清单增量**内联在超级块页里**（`INLINE_MAX = 80` 条；**第 16 轮格式 v2**，v1 是 32 条 / 40 B 头 / 40 B 项，
挂载时按魔数分流、第一次写 SB 自动升级，见 ROUND16 §1）：

```
[0..48)  超级块头（magic 'FCS2' / fmt / vers u64 / state / chk / tail / man_* / nman / n_inl）
[48..)   本次提交的 ManEnt 增量（每条 48 B：seq/ver 64 位；op 新增 M_RUN_TRIM=7、M_RUN_HOLE=8 预留）
```

- 攒够 80 条才落一页清单（'MAN2'，85 条/页；老库链里的 'MANC' v1 页逐页按魔数分辨），清单页数超过 64 就写一次全量快照；
- 提交原子性靠 **CRC 覆盖整段载荷**（`48 + 48×n_inl` 字节）：载荷没写全 ⇒ CRC 对不上；
  写全了就是一次完整提交；
- NOR 只允许 1→0：超级块槽先 `erase` 再整页写，数据页只在**提交点落盘之后**才擦除复用。

清单条目里 **`M_SEG_DEL` 必须带 `(cell, rid, seq)` 三元组**——因为页号会被复用，
只带 rid 会在重放时删错段。同理 `Run::seq` 必须持久化，否则合并出来的 run 在重开后
排序位置改变，读到的就是旧值。

### 7.1 run 元数据页：挂载从 O(总页数) 变成 O(run 数)

run 是**不可变**的：一旦封好，它的 `fences`（每页首键）、`pbytes`（每页记录字节）、
`pnrec`（每页条数）、`sp`（稀疏块）、`bloom` 就再也不会变。这些都是**派生量**，
原来每次挂载都要把整库的每个数据页读一遍、逐条解码重建一遍。

现在封 run 时顺手把它们存成 `PK_RMETA` 页，**紧跟在数据页区间之后**（`page0+npages` 起）：

```
每页： u32 magic('META') | u32 idx | u32 npg | u32 crc32(payload) | u32 len | payload
页 0 载荷头 56 B：magic2 page0 npages nrec nbytes nsp nkid bwords bits self_npg first last
其后： fences[8/page] pbytes[4/page] pnrec[2/page] sp[20/16条] kidx[8/键] bloom[8/64bit]
```

几个刻意的选择：

* **不改清单格式**。meta 的位置是算出来的（`page0+npages`），不需要新的清单项，
  于是清单快照、增量批、崩溃语义全部原样复用；
* **惰性读**。清单链里大量 run 是「加了又删」的（快照之后被合并掉），给它们读 meta 是白花钱。
  `apply_man` 只记一个 `meta_pending`，真正活下来的 run 在 `attach_run` 里才 `ensure_meta()`。
  这一条把 400k 档的 `replay_manifest` 从 27 ms 压到 **0.2 ms**；
* **校验对账**。每页自带 CRC，且逐字段与清单条目核对（`page0/npages/first/last/nbytes/self_npg`）。
  任何一处对不上就退回「逐页扫描重建」的老路 —— 老文件、半写页、被复用的页都走这条路；
* **小 run 不写**（`npages < 16`）。1 页数据配 1 页 meta 是 100% 的空间开销，小设备上会
  直接把引擎逼死（r2 用 96 页设备把这条试出来了）；阈值 16 页后 meta 开销 ≤ 6%，
  而 ≤16 页的 run 挂载时直接扫也就 16 页。
* **空间紧时能放弃**：`alloc_pages(npages+mnpg)` 拿不到就退回只分配数据页，meta 缺失
  ⇒ 挂载扫描。宁可慢，不可写不进去。

代价（明说）：meta ≈ **3.25 B/记录**（bloom 2 B、sp 1.25 B、页数组 ~0.1 B），约数据量的 1.7%，
反映到 bench3 的写放大是 **+0.17 ~ +0.20**（2.53× → 2.70×，2.57× → 2.77×）。
买到的是一次 O(runs) 的挂载，见 §10.6。

**本轮补的两件事（B1 / 缺口 ④）**：

1. **策略可配**：`set_rmeta_mode(false)` 整体关掉（省 1.7% 写放大，重开退化为扫全库）；
   `set_rmeta_min_pages(n)` 只给大 run 写（小 run 的 meta 本来就是 100% 开销）。
   两个都是纯运行时旋钮，不改格式 —— 关掉的库照样能被开着的一端打开。
2. **自愈**：`checkpoint()` 会调 `heal_missing_meta(512)`，给"没有 meta 的活 run"补一份。
   优先**原地**补（meta 就在 `page0+npages`，只要那几页正好空闲就写进去，**0 字节数据重写**）；
   拿不到连续空闲才退回"重写整条 run"（受页预算约束）。
   `tests/m1.cpp`：清掉 20 个 run 的 meta ⇒ 重开 `meta_hits=0` ⇒ `checkpoint()` ⇒
   重开 **`meta_hits=20`**、`verify` 0 错。

   > 踩到的坑：`build_rmeta()` 会把 `r->mnpg` 写进页内的自我描述字段（`selfpg`），
   > 原地补写前必须先把 `r->mnpg` 设成新值，否则加载时的自校验会把这份新 meta 判成坏的
   > （现象是 `heal=20` 但 `hits=0`）。

## 8. 组提交：把 N 次逻辑提交摊成一次物理提交

```cpp
s.commit(false);   // 逻辑提交：版本前移，O(1)，零 I/O
...
s.commit();        // 物理提交：一次 flush + 一个提交点（默认参数）
s.sync();          // 同上，语义更直白
```

- 逻辑提交只承诺"这组写要么整体可见、要么整体不见"，**持久性由 sync 承诺**；
- 攒批期间数据留在内存表里，`get`/`select` 立刻可见（版本号已经前移）；
- `abort()` 不会丢掉"已逻辑提交"的数据：它先补一次物理提交，再清工作区；
- 掉电丢失的是"最后一次同步之后的逻辑提交"，这与 WAL 的 `synchronous=OFF/NORMAL` 同构。

组提交摊薄的是三样东西：页尾取整、提交点页、清单增量。实测（bench3）：

| ops / commit | 单提交落盘 | 组提交 8:1 |
|---|---|---|
| 20000 / 500 | 3.17× | **1.69×** |
| 20000 / 100 | 4.16× | **1.75×** |
| 50000 / 1000 | 2.81× | **1.67×** |
| 200000 / 2000 | 3.99× | **2.45×** |

### 8.1 异步组提交：`commit(false)` 的 flush 放后台

`set_async_writes(true)` 之后，`commit(false)` 不再只是版本号前移：

- 攒够 `async_flush_min()` 条（默认 65536）**或** 4 MB 工作区，就把这批记录打成一条 run，
  页写交给后台线程（`enqueue_batch`：整批一次加锁、一次唤醒），前台立即返回；
- 页仍然遵守 `pending_free_` 纪律：**只在提交点之后才允许复用**，所以后台写永远踩不到
  "还挂在旧清单上"的页；
- 读路径在 `page(pid)` 里 `wait_page(pid)` 兜底：读到自己还没落盘的页就等它；
- 真正的提交点（`commit()` / `sync()`）先 `wait_io()` 再写提交记录 ⇒ **数据永远在提交点
  之前**，这个顺序不因异步而改变。掉电丢的仍然只是"最后一次同步之后的逻辑提交"（f3 逐点验证）。

**为什么阈值必须是字节数而不是"每个逻辑提交都落一段"**：每落一段就是一条与全键域重叠的
run，run 一多，后续合并级的代价会盖过重叠收益。实测（200k 插入、每 500 条一次逻辑提交）：

| 后台落盘粒度 | 插入 µs/op | run 数 | 备注 |
|---|---|---|---|
| 每 8192 条 | 9.3~10.2 | 24 | 碎片化，合并风暴 |
| 每 16384 条 | 1.5~1.7 | 12 | 巧合的好点 |
| 每 65536 条 | 4.0~4.1 | 3 | |
| 4 MB 写缓冲（默认） | **4.3~4.6** | 2 | 与关闭异步持平，峰值内存 1/3 |

所以默认值是"写缓冲 4 MB"，**默认不开异步**：它买到的是**峰值内存**和**停顿上界**，不是吞吐。

`set_io_threads(k)` 把一批页分给 k 个工作线程（`FileDev` 用 pread/pwrite，RamDev/NorSimDev
本来就是按页 memcpy）：k=1/2/4 的吞吐差异在本机噪声内（1.5~1.9 µs/op），收益留给真机队列深度。

### 8.2 失败语义：提交是原子的，错误是粘性的

- **先落页，再动账**：`flush_mem` 的存活账（`c->live/c->dead`、`run->live_*`）
  在 run 写成功**之后**才更新；写失败（`NOSPACE`/`IO`）时账目原样不动，
  `mem_` 还留着，调用方重试即可。旧实现先把账扣了再写，一次失败就永久漂移。
- **失败即回到上一个提交点（延迟执行）**：`commit()` 在动过账之后的任何一步失败都会把
  状态标记为"脏"，下一次公开调用先按盘上的清单重建内存态（`reload`），`mem_`/`pend_delta_`
  全程保留 —— 所以"提交失败"不会留下半套状态，重试就从干净状态继续。
  之所以延迟到下一次调用，是因为重建要等 I/O；放在失败路径里会让"设备卡住"变成
  "调用方也跟着卡住"（见下一条）。
- **后台写失败必须上抛**：worker 把失败记在 `io_err_`，`wait_io()` 之后
  `commit()` 比对计数，变了就 `reload()` + 返回 `RC::IO`。旧实现只自增不读，
  异步写失败被静默吞掉、提交照样返回 OK（`r2` 阶段 3 抓的就是它）。
- **重建状态前必须 `wait_io()`**：`reload()`/`rollback()` 都要等在飞的页写完。
  否则 worker 会把**旧分支的页**写到刚刚被重新分配出去的位置上 ——
  表现为随机坏清单项。这是本轮最难查的一个 bug。
- **等待必须有界**：`set_io_timeout_ms(ms)` 之后，`wait_io()`/`wait_page()` 到期就返回
  `RC::TIMEOUT`，绝不无限挂在条件变量上。一次超时会把 store 置入"停滞"状态
  （`io_stalled_`），**后续等待全部快失败**，所以一次调用只会付出一个 timeout 的代价，
  而不是"每页各等一轮"（`r2` 阶段 5：设备写卡 3 s、超时 150 ms ⇒ 提交在 **150 ms** 内
  返回 `TIMEOUT`，而不是 6 s 或永远）。队列排空后自动解除停滞。
- **提交失败 = 打脏标记，不在原地重建**：失败路径若就地 `reload()`，重建本身要等 I/O，
  设备卡住时会把调用方拖住。现在的做法是置 `dirty_` 并立刻返回；下一次任何公开调用
  （`get/put/del/commit/verify/cursor/...`）先 `ensure_ready()` 按盘重建，重建等不到
  就继续返回 `TIMEOUT`。这样"失败"和"恢复"都是有界的，且 `mem_` 全程保留。
- **清单项自证清白**：`apply_man` 对 `M_RUN_ADD` 校验
  `0 < npages ≤ cap`、`page0 ≥ 2`、`page0+npages ≤ cap`，越界直接丢弃并计数
  （`bad_manifest()`）。旧实现照着 `m.npages` 分配 `fences/pbytes`，
  一条坏记录就能申请 9 GB 内存并 `bad_alloc`。

| `Run::sp` | 16 条/块 | run 级键域摘要（精确跳过，纯 RAM） |
| `Run::kidx` | 8 B/键 | 可选精确键索引（`set_key_index`） |
| `io_timeout_ms` | 0（不限） | 有界等待（`set_io_timeout_ms`）；>0 时任何等待到期都返回 `RC::TIMEOUT` |
| `PageId` | **u32** | 页号 32 位：单库 2^32 页 × 4 KB = **16 TB**（u16 时代是 256 MB，且越界会静默回绕） |
| `SP_SHIFT` | 12 | 段摘要 `sp` 的打包：`页<<12 \| 偏移` ⇒ 20 位**run 内**页号 + 12 位页内偏移 |
| `SP_MAX_PAGES` | 2^20 | 单条 run 最多 4 GB（20 位页号）。超过之后 `sp` 只是不再新增条目（它本来就是提示，probe 从最后一条线性往后扫，仍然正确、只是慢） |
| `INLINE_VAL_MAX` | **3000** | 值 ≤ 3000 B 内联在数据页；更大走溢出链（`set_overflow(false)` 退回旧行为） |
| `OVFL_MARK` | 0xFFFF | 页上 `len` 字段的哨兵：这条记录的值体是 16 B 溢出描述符（⇒ 65535 不能当值长） |
| `OV_CAP` / `OV_HDR` | 4080 / 16 | 溢出页有效载荷 / 溢出页头（`'OVFL'`\|next\|off\|len，自身 CRC 覆盖头+载荷） |
| `rmeta_min_pages` | 16 | 小于这么多页的 run 不写 meta（`set_rmeta_min_pages`，`FCS_RMETA_MIN_PAGES`） |
| `MAN_SNAP_AT` | 64 | 清单链上限（超过写全量快照） **+ 范围墓碑也走这条链**（`M_RANGE`） |

**单次操作复杂度**

| 操作 | 代价 |
|---|---|
| `put` | O(log n) 内存表 |
| `commit` | O(本次记录) 顺序写 + O(1) 元数据 + 压实预算内 O(k) 页 |
| `commit(false)` | **O(1)，零 I/O**（开异步时：O(这批记录) 顺序写，不等 I/O） |
| `get` | ≈1 页读（Bloom 门控，与 run 数几乎无关） |
| `select` / `scan` | k 路归并（k=run 数），顺序读 |
| `split` | O(段数) 视图操作，**0 字节搬移** |
| `put`（大值） | 额外 O(值/4080) 页**顺序写溢出链**（在 put 时落盘，不等提交） |
| `del_range` | O(1) 记一条待落清单的墓碑；查询侧 O(墓碑数) 二分判定 |
| 回收 | 整 run 死 ⇒ 0 写；否则 ≈ 活字节 |

## 10. 实测

### 10.1 同负载写放大（随机键，bench3）

| ops / commit | 写放大（元数据页之前 → 之后） | probes/get | 段数峰值 | 耗时 | verify |
|---|---|---|---|---|---|
| 20000 / 500 | 2.53× → **2.70×** | 0.12 | 9 | 0.033 → 0.029 s | OK |
| 20000 / 100 | 3.44× → **3.63×** | 0.12 | 14 | — | OK |
| 50000 / 1000 | 2.21× → **2.35×** | 0.27 | 19 | 0.069 → 0.063 s | OK |
| 200000 / 2000 | 2.57× → **2.77×** | 0.65 | 7 | 0.372 → 0.333 s | OK |

写放大涨的 0.17~0.20 全部来自 §7.1 的 run 元数据页（≈3.25 B/记录，数据量的 1.7%）：
它换来的是挂载从 45 ms 掉到 12 ms（§10.6）。去掉它写放大立刻回落，但每次重开都要把整库
重新解码一遍 —— 这笔账在这里明写出来，是个**可以按场景调的取舍**（`FCS_RMETA_MIN_PAGES`）。

提交越碎，段越多、写放大越高（每次提交都要重写被覆盖的页 + 分层合并），这就是 §8 组提交
存在的理由：把 N 次逻辑提交摊成一次物理提交，写放大直接掉一半以上。

**写放大花在哪**（`bench3` 现在直接打出来，200000 / 2000）：

| 段 | 字节 | 占活数据 | 说明 |
|---|---|---|---|
| flush | 4.08 MB | 1.32× | 提交时把 memtable 顺序写下去，页尾填充不可避免 |
| merge | 3.32 MB | 1.07× | 分层合并搬活记录 |
| manifest | 0.58 MB | 0.19× | 每次提交的清单增量页 |
| **合计** | 7.98 MB | **2.57×** | 活数据 3.10 MB |

两个旋钮的实测（同一负载，200000 / 2000）：

| 改动 | 写放大 | 读页 | 耗时 | 段数峰值 |
|---|---|---|---|---|
| 旧：`FCS_LVL_DIRTY_PCT=20` | 3.14× | 55 258 | 0.95 s | 23 |
| 新：门槛 30% | 2.57× | 50 346 | 0.40 s | 7 |
| 再 + 清单页只写 `MHDR+n*MENT` 字节 | 2.57× | 50 346 | **0.36 s** | 7 |

门槛从 20% 提到 30% 是这一轮最划算的一刀：20% 时「刚写下去就被覆盖」的层会被反复重写，
写下去的全是马上要扔的数据；30% 之后同样一层的垃圾攒够了再合并，写放大 3.14×→2.57×、
耗时降到 1/2.5、段数峰值 23→7（读放大反而更好）。

**同一负载的耗时**（200000 / 2000，本轮修复前后）：

| 版本 | 读页次数 | 总耗时 | 说明 |
|---|---|---|---|
| 修 Bloom 之前 | 205 528 | **16.29 s** | run 级存活账永远算满 ⇒ 零写回收完全失效，run 越堆越多 |
| 修 Bloom 之后 | 81 245 | **0.95 s** | 整条 run 全死 ⇒ 直接摘链，读页少 2.5 倍 |
| 现在（门槛 30% + 清单页按需写） | **50 346** | **0.36 s** | 合并次数少了，读放大反而更好；写放大同时降到 2.57× |

另外 `merge_run_set` 的 `recount` 从"全库所有单元"收窄为"这次合并牵动的单元"
（本例 206 → 约 5 个），长跑里不再有 O(单元数) 的固定开销。

### 10.2 与 SQLite 正面对比（bench4，同负载同批次）

50000 键 / 32 B 值 / 每 500 次操作提交 / 区间扫 100 行 × 2000 次；
SQLite `WAL + synchronous=FULL + cache_size=16MB`，FCS `FileDev` + 提交屏障。
四档 FCS：①同步组提交 ②异步组提交 ③②+`compact_file()` ④③+有序键。

| 阶段 | ① 同步组提交 | ② 异步组提交 | ③ 异步+整理 | ④ 有序键+整理 | SQLite 3.46 |
|---|---|---|---|---|---|
| 写入（含提交） | 0.94~1.63 | **1.00~1.11** | **1.02~1.16** | 1.00~1.10 | 2.3~8.4 |
| 覆盖写 | 0.82~1.41 | 0.86~2.33 | **0.85~1.01** | 0.85~1.03 | 14~44 |
| 点查 | 0.49~0.54 | 0.49~0.56 | **0.46~0.47** | 0.47~0.51 | 1.66~3.47 |
| 区间扫描（100 行） | 1.61~1.65 | 1.55~1.63 | **0.54~0.56** | 2.00~2.99 | 1.63~2.21 |
| 空间（文件） | 2.90 MB | 2.90 MB | **2.10 MB** | **1.87 MB** | 2.35 MB |
| 每记录字节 | 58.1 B | 58.1 B | **41.9 B** | **37.4 B** | 46.9 B |

> 共享 CPU，2 次运行的范围。SQLite 的写入/覆盖写抖动最大（2.3~8.4 / 14~44 µs），
> 取全部样本的范围；FCS 的写入已稳定在 1 µs 量级，抖动主要来自末尾的整理。

**读**：区间扫描的 k 段归并被 §3.3 压到 2 以内，点查 `misses/scan=0`，游标与页缓冲
全走固定数组、扫描期零分配。整理后 run 只剩 1 条，区间扫描再快 3 倍（1.6 → 0.55 µs）。
**写**：B+ 树每次更新原地改页 + WAL 记一份；FCS 只追加一条 run，旧副本靠"整 run 清零 +
分层合并 + 归一"批量回收。覆盖写比 SQLite 快 15~40 倍：FCS 的更新是"追加 + 记账"，
不碰旧页，也不写 WAL。
**空间**：整理后文件 **2.10 MB**，小于 SQLite 的 2.35 MB；有序键再省 11%（1.87 MB）。

### 10.5 空间回收：把高水位还给文件系统

`compact_file()` = 归一（全库一条 run）→ 搬家（重写到最低空闲整块）→ 清单检查点 →
尾部回落（`shrink()` 截断文件）。bench4 里 27.9 MB 的预分配文件（2.90 MB 高水位）这样变成
**2.10 MB**；`f5` 里 60 万次覆盖写后的收缩是 **2467 → 125 页（9.6 → 0.5 MB）**，前后逐键对拍一致。

| 步骤 | 作用 | 代价（50k × 32 B） |
|---|---|---|
| `consolidate(0)` | 全部 run 合成一条，垃圾一次性消失 | 一遍读写 ≈ 10 ms |
| `relocate()` | 把 run 搬到最低的空闲整块（只往下搬） | 一遍重写 ≈ 6 ms |
| `checkpoint()` | 清单重写成一份紧凑快照并回收旧链 | 几十页 |
| `shrink()` | 高水位收到最高引用页，`ftruncate` | 0 |

搬家只往低处搬：目标块必须**低于** run 现在的起始页，否则等于把文件撑大。
装不下（碎片化）就原地不动——收缩率会差一些，但绝不牺牲正确性。
增量版 `consolidate(N)` 只压"段数 ≥ N"的单元，避免整库重写。

### 10.4 分层旋钮 `lvl_t`（读优化 ↔ 写优化）

同一负载（50k × 32 B，异步组提交 + 整理）：`lvl_t` 只影响**中途**的 run 数，最后一次归一
把所有 run 抹平，所以 8/16/32 的终态完全一致，只有 4（合并最频繁）明显更贵：

| lvl_t | 写入 µs/op | 点查 µs | 区间 µs | 文件 |
|---|---|---|---|---|
| 4 | 1.87 | 0.47 | 0.55 | 2.10 MB |
| 8（默认） | **1.11** | 0.46 | 0.54 | 2.10 MB |
| 16 | 1.13 | 0.46 | 0.54 | 2.10 MB |
| 32 | 1.15 | 0.47 | 0.58 | 2.10 MB |

不整理时差异才会显现（§10.1 的写放大就是 `lvl_t=8` 下的结果）：批量导入用 16~32 省写，

### 10.3 热点覆盖负载（GC 压力测试，2000 键反复覆写）

| ops / commit | 写放大 | 空间放大 | probes/get |
|---|---|---|---|
| 20000 / 200 | 4.40× → 见 §5.1 | 1.49× | 1.01 |
| 50000 / 200 | 4.53× | 1.82× | 1.01 |
| 50000 / 500 | 3.51× | 1.75× | 1.00 |

写放大 3.5~4.5× 是**主动选择的平衡点**：`FCS_GC_RATIO=3` 可把写放大压到 3.9×，
但空间放大升到 3.3×；`=1` 则空间 1.45×、写 5.1×。默认 2 落在拐点上。

**run 级存活账必须精确**（`tests/f6.cpp` 守着）。它是「整条 run 全死 ⇒ 零写回收」和空间
收敛的唯一依据，也是 `verify()` 的硬检查项。这一轮把它从「增量提示值」改成了段级精确记账：
每个 `Seg` 记「本单元内由它胜出的记录数」，`run->live_recs` 恒等于它在所有单元里的 `live` 之和。
好处是口径与 `verify()`（逐单元归并）**完全同一套**——不管压实产物和合并产物同不同 seq、
是不是跨单元，都对得上。改之前热点覆盖负载（2000 键反复覆写）会出现「一条 run 记 118 条活、
真值 40」，于是永远不满足回收条件，空间缓慢膨胀；改之后同样的负载 `verify` 一次不报错。

### 10.7 点查微基准（隔离设备）与两路组相联

页内二分的效果必须和「读页次数」分开看，否则会被设备抖动淹没。`/tmp/probe2.cpp` 用
200000 条记录 + 4096 个热键反复点查（工作集常驻缓存），纯 CPU 口径：**830~950 → 296~370 ns/get**。

页缓存从**直映**改成**两路组相联**（`page()` 先查同集合的两路，踢更旧的一路）。
直映的问题在归并/压实这种「同时摸 k 条 run 的页」的访问模式下最明显：两条 run 的当前页
只要同余就互相踢出，k 路归并的读页次数直接翻倍。实测 bench3 200000/2000 的 `read_ops`
50 344 → **49 556**（-1.6%，这本就是缓存命中的边界场景）；`arena=2048` 页在 2887 页的库上
工作集本来就不够，收益有限，但代价是 0（同样的内存、同样的「指针只活到下一次 `page()`」契约）。

### 10.8 大值：溢出页（A2）

`put()` 的值上限从「3992 B（一页放得下）」提到 **65534 B**。≤3000 B 仍然内联
（小值是 OLTP 的绝大多数，内联意味着零额外页、零额外读）；更大的值在 `put()` 里
**当场**写成一条溢出链，内存表里只留 16 B 描述符：

```
数据页记录：  key(8-pfx) | len=0xFFFF | {pg0, npages, total, crc32}(16 B)
溢出页：      'OVFL' | next | off | len | data(≤4080)   ← 每页自带 CRC
```

一条链是**一次 `alloc_pages` 拿到的连续区间**，所以释放只需要 `(pg0, npages)` 两元组，
不需要页表；`free_pages()` 也就能像普通页一样回收它。

| 值长 | 4000 键 | 写 | 读 | 物理页 | 空间放大 |
|---|---|---|---|---|---|
| 3001 B | 4000 | 12.2 MB | **1.66 GB/s** | 4026（含 4000 链页） | 1.34× |
| 8160 B（=2×4080） | 2000 | 16.4 MB | **1.54 GB/s** | 4012 | **1.00×** |
| 8192 B | 2000 | 16.5 MB | **1.99 GB/s** | 6012 | **1.50×** |

> 写吞吐在宿主 FS 上抖得厉害（同一负载 0.17~1.4 GB/s，页缓存 + overlay 的共同作用），
> 所以这里只把**读**当稳定数字；写只报"没有塌方"。复现：`make bench && build/bench5 big 8192 2000`。

**取舍写清楚**：

1. **空间放大会在 4080 的边界上跳变**。8192 B 需要 3 页（12240 B）而不是 2 页，
   空间放大 1.5×；8160 B 正好 2 页，放大 1.00×。要精确控制，就把值对齐到 4080 的倍数。
   这是"页式存储"的固有代价，不是实现缺陷——除非把多个值打包进同一条链（那要跨值引用计数）。
2. **`put` 就落盘**。好处是提交时不用再搬大值、内存表不会被几条大值撑爆；代价是
   `put` 可能返回 `NOSPACE`（以前只有 `commit` 会），而且**未提交的链已经占着盘**。
   提交失败时这些链由下次挂载的 `rebuild_free()` 回收（它会把活 run 的链算作已用，
   其余的自然是空闲）。这个"泄漏窗口"在 §14 里继续列着。
3. **压实会重写链**。归并产物拿到的已经是物化的真值，`w.add()` 于是分配**新链**，
   旧 run 摘链时 `free_ovfl_of()` 释放旧链。所以压实期间的空间峰值 ≈ 2×大值总量。
   没做"共享链 + 引用计数"：那要改清单格式（记 refcount）和所有释放路径，本轮不做。
4. **`verify()` 会顺着每条链读一遍**（页头/CRC/总长/链尾），所以大值库的 `verify`
   是 O(值总量) 的 I/O。`Report.ovfl` / `Report.ovfl_pages` 给出链数和链占页数。
5. **回退（`rollback`）不会删掉链**：和 §12 之 33 一个道理，回退恢复的是逻辑视图，
   物理页由下次挂载的统一回收兜底。

自动回收验证（`tests/v1.cpp` 最后一段）：同一个键反复写 8 KB 共 40 轮，
`used` 首轮 5 页 → 峰值 11 页 → 结束时 **11 页**（不涨），`verify` 干净。

### 10.9 扫描预读（B2）

单段顺序扫描时，游标按 8 页窗口发一次 `read_multi`（一次 `pread` 读 8 页再 `memcpy` 分发），
命中率/统计口径不变（预取不算 `hits`/`misses`）。多路归并时自动关闭（互相踢只会更差）。

`build/bench5 scan 128 20000`（FileDev + 20000 条 60 B 值，arena 只有 128 页）：

| 预取 | pread 次数 | 读字节 | 耗时 |
|---|---|---|---|
| 关 | **317** | 1268 KB | 0.55 ms |
| 开 | **58** | 1268 KB | 0.58 ms |

调用次数 **5.5× 更少，读的字节一模一样**。本机 `pread` 只需 ~0.5 µs（页缓存全热），
所以耗时没变；真 NVMe 上一次 pread 是 50~100 µs，这一项就是 300 次 × 70 µs ≈ **21 ms → 4 ms**。

**取舍**：arena 够大时预取会多读（256 页 arena：25 次 pread/316 KB vs 65 次/260 KB，
多读 21% 的字节）。也就是"用带宽换延迟"，块设备上都划算，`set_prefetch(false)` 可关。

### 10.10 多写者 + 自动组提交（B3）

`put`/`del`/`commit`/`get`/`select`/压实/快照全部串在一把 `std::recursive_mutex` 上。
`commit()` 开头先看一眼：**如果这次提交没有任何新写（`wr_gen_ == durable_gen_`），
就直接返回 OK**，把物理提交让给已经走在路上的那个人——这就是"自动组提交"。

| 负载 | 墙钟 | 说明 |
|---|---|---|
| 1 线程 × 20000 条，每 10 条提交 | 311~624 ms | 单线程基线 |
| 4 线程 × 5000 条，每 10 条提交 | 207~428 ms | **1.4~1.5×** |
| 自动组提交合并掉的提交 | 3~9 次/轮 | `commits_merged()` |

**明说天花板**：只有 1.4~1.5×，因为 `flush_mem`（O(内存表) 遍历）和 `commit_delta`
（清单页 + 超级块）都在锁里。要再往上走得把 RunWriter 的"写页"阶段移出锁
（分配 `free_`/`tail_` 仍要锁），那是下一轮的事。**正确性不打折**：`w1` 用 4 线程 ×
5000 条断言逐键回读 + `verify` 零错；`make asan` 里这一项额外跑一遍 **TSan**，无 data race。

### 10.11 容量：32 位页号（A1）

`PageId` 从 u16 改成 u32，同时把段摘要 `sp` 的打包改成 `页<<12|偏移`（先改打包、再放宽
类型——反过来会在页号 >65535 时**静默**把页号截成余数，不报错，只是漏读）。
单库上限 65535 页（256 MB）→ **2^32 页 = 16 TB**。

`tests/b1.cpp`（`make test` 最后一段，约 2 s、1.56 GB 设备）：

```
A: 66000×3900B（溢出链）高水位=66773 (261 MB) 活页=66773 (261 MB) runs=2 verify=0
B: 30000×2900B（内联）  高水位=96905 (379 MB) 活页=96541 (377 MB) runs=8 verify=0
compact_file: rc=OK  高水位 96905 → 127795（活页 96901，含链）
reopen 85.6 ms  verify 145.6 ms  errors=0 回读坏=0 meta_hits=7 runs=1
```

- **A 段**把 `page0` 推到 65535 以上（每条 3.9 KB 值 = 1 链页 + 1 数据页），
  专打 `sp.packed>>16` 那条旧截断路径；
- **B 段**是内联大值的**大 run**（每条 2900 B，一条 run ≈1500 页），meta 页贴在
  `page0+npages`，页号同样在 65535 之上；
- **高水位 ≠ 活页**：差的是合并/压实留下的、已回收但仍在高水位以下的页。
  这两个数必须分开报，否则会把"碎片"读成"数据"（`live_page_count()` = 高水位 − 空闲）。
- **`compact_file` 这一轮在这里从"缩不了"变成"缩不了、而且会涨"**：
  8 条 run 归一成一条 ~21000 页的 run，而大值库的低位全被链页占着（链只随 run 搬），
  连续块只能落在尾部 ⇒ 96905 → 127795（+31%），活页 96901。
  数据是对的（`verify` 0），这是 §12 坑 61 的已知取舍；解法是链的引用计数（§14 第 5 条）。
- 重开 ~150 ms，其中 `verify` 209 ms 是**顺链读回全部 3.9 KB 值**的代价；
  纯挂载（不含 `verify`）在 `-DFCS_TIME_OPEN` 下仍是 0.65 ms replay + 2.0 ms attach +
  95 ms 存活账（存活账随记录数线性，和容量改造无关）。

### 10.12 范围删除：清单墓碑（缺口 ②）

`del_range(lo, hi)` **不进键空间** —— 它只在清单里落一条 `M_RANGE{key=lo, last=hi, ver}`。
这样做的理由很硬：如果把"范围"塞进键空间（比如写一万条单键墓碑），要么扫描必须认识
一种新的记录类型（连带 `merge_emit`/`Cursor`/`flush`/`verify` 全都要改），要么就得
在 `put` 时展开成 N 条（N 不可知，且立刻炸写放大）。放进清单的结果是：

- 扫描/游标/归并**一行都不用改**（墓碑不产生记录）；
- `get` / `Cursor::next` / `merge_emit` 三处各看一眼 `range_hidden(k, ver, view)`；
- 判定规则只有一句：**存在一条 `lo ≤ k < hi` 且 `ver >= 记录版本` 的墓碑 ⇒ 这条记录不可见**。
  同一次提交里"先 `del_range` 再 `put`"也会被盖住（同版本算墓碑更晚）—— 这条规则写死在
  `commit_delta()` 里，免得以后靠猜。

`tests/g1.cpp`（10000 键，删 `[4001, 7001)`）：

```
删除后可见 7000 条（get(5000)=NOTFOUND、get(3000)=OK、get(7001)=OK  ← 右开区间）
删后再写 5555 ⇒ 可见（版本更新）
重开：range_tombstones()=1，可见 7001 条，verify 0
consolidate(0)：墓碑清零（被盖住的记录在归并时真的被丢掉了），used 43 → 80
再重开：墓碑仍然 0，get(5000)=NOTFOUND（**不会复活**）
```

**取舍**：

1. **墓碑是清单项**（40 B/个）。几千个范围删除会把清单撑大（`MAN_SNAP_AT=64` 之后每次提交
   都要写全量快照）。`consolidate(0)` 会物化并清空墓碑；**自动**归一（墓碑数阈值触发）
   列在 §14 第 6 条，本轮没做。
2. **归一后有快照时不清墓碑**（`nsnap_>0` 时保留）：老快照仍要看到"当时还没删"的版本。
3. **墓碑不回收空间**：它只影响可见性，物理记录要等归一/压实才消失。归一后 `used` 反而
   短暂变大（43 → 80），因为归一本身是"重写整库"；旧页要等 `shrink()`/`compact_file()`
   才还给文件系统。

### 10.13 压实/归并的"零写接管"（H）：大值不再是压实的负担

**问题**：压实/归并是"重写活记录"，而一条 8 KB 的值在页上只占 16 B 描述符。
如果不做特殊处理，重写 = 把每个大值读出来再写一条新链 ⇒ 压实成本被**值的字节数**支配，
而不是被"记录数"支配。`v1` 里 40 轮覆盖后空间不涨是对的，但每次压实都把全部大值搬了一遍。

**做法**（三件套，都在 `include/fcs.h`）：

1. **`AOVL` 附件**：每条 run 在 `page0 + npages + mnpg` 追加一小段附件，记
   `(数据页, 描述符偏移)` 列表 + `data_pg0` + CRC（`np<=8`，超过就不写）。
   挂载后要"这个 run 的链都在哪"不必读数据页（`ensure_ovfl_loc`）。
2. **`add_take()`**：归并时若赢家是溢出值、且**源 run 这次一定会死**，新 run 只照抄
   16 B 描述符，链原地不动（0 字节读、0 字节写）。
   判据 `take_ok(src, dsc) = ovfl_take_ && nsnap_==0 && d.npages && take_set_.count(src->page0)`：
   所有权是**按 run** 记的，只有"这次操作里必然被摘掉"的源 run 才能交出自己的链
   （`compact_cell` 用 `count_refs(rid)<=1`，`merge_run_set` 用全部 src）。
3. **只算账的遍历不读值**：`merge_emit(..., need_vals=false)`，`recount`/`verify`/
   `check_liveness` 只取页内 16 B 指针。

**数字**（`bench5 consol`：2000 键 × 8192 B，8 条 run，8 次提交，同一台机器）：

| 模式 | runs | consolidate 耗时 | 读页 | 写页 |
|---|---|---|---|---|
| `consol 0`（关接管：老路，值重写） | 8 → 1 | **66.8–68.8 ms** | 2004 | **6023** |
| `consol 1`（开接管） | 8 → 1 | **1.4–1.7 ms** | **4** | **23** |

- 写放大 **−99.6%**（6023 → 23 页）：老路必须为 2000 个大值**重新分配链**，
  接管只写索引页（23 页 = 数据页 + meta + 附件）。
- 读放大 **−99.8%**（2004 → 4 页）：老路要把 24.6 MB 值全部读出来，接管一个值都不读
  （描述符在页上，链在附件里能定位到）。
- 耗时 **≈40×**。两者 `verify` 都是 OK（`consol` 跑完会逐键校验 2000 个值）。

**顺序读的顺带收益**：`read_ovfl` 知道链是 `alloc_pages` 给的**连续**页，所以按 8 页一批
`read_multi`，并且**不经过页缓存**（链写一次就不变，别把数据页缓存踢干净）。
2000 个 8 KB 值（每条链 3 页）全扫：`pread` **6050 → 2000**（一条链一次），
3.1~6.1 ms / 24.6 MB（≈4~8 GB/s，看热缓存状态）。链越长收益越大：16 页的链是 2 次 pread 而不是 16 次。

**取舍**：
- 每个含大值的 run 多 **2 页**附件（小库 33 → 35 页；`v1` 的 40 轮覆盖 11 → 13 页峰值）。
- 附件写失败/超 8 页 ⇒ 自动降级为"挂载时扫数据页"（不报错，只是慢）。
- 接管的前提是"源 run 必死"。有快照时（`nsnap_>0`）一律不接管——那时源 run 不能死。
- `compact_file()` 想**真的缩小文件**就不能全靠接管：链留在老位置，高水位下不来
  （§12 坑 61）。

都要测：`g5` 的 `FuzzDev` 按种子切换 `whole`。

**A3 交错模糊 `g5`**（`tests/g5.cpp`，"mini model checker"）：`FuzzDev : RamDev`（随机 20~200 µs 慢写、`whole` 开关）；
op 流按千分比混合 put 480 / del 80 / del_range 20 / get 120 / select 30 / commit 50 / commit(false) 60 / snapshot 25 /
rollback 15 / forget 20 / 维护 55 / scrub 10 / reopen 10 / verify 25；模型 `truth`（当前逻辑状态）、`durable`
（上一个提交点）、`snaps[k]`；每 2000 步全量逐键比对；种子决定 async / io_threads / arena / whole / slow_pct。
默认 4 种子 × 12000 步 **≈3 s**；1~60 种子扫过、seed 3 跑 100k 步 8.5 s。**第一轮就抓到 7 个 bug（坑 74~80）**，
全是单元测试覆盖不到的交叉路径（未提交大值 × shrink、del_range × 同批 put、del_range × compact_file、重放 × 页号复用）。

**随 A3 一起定下来的三条语义**（都是修 bug 的结果，不是新功能）：
1. **读己之写**：put/del/del_range 一经调用，`get`、`select`、`count`、`scan`、`index_scan` 立即可见
   （以前只有 `get` 看得见 put/del，`select` 要等数据进 run，`del_range` 要等提交）。实现：游标多归并一路
   "内存表键序视图"（`mem_sorted()`，按 `MemTable::gen()` 缓存、按追加段增量归并），范围墓碑在 `del_range`
   时就登记进 `ranges_`（版本 = 发出时刻）。
2. **维护操作 = 提交点**：`consolidate/relocate/checkpoint/compact_file` 先 `commit()` 再动页（没有未提交的写时短路）。
   `shrink` 只写 SB，不是提交点。`reopen` 之后的状态**恰好**等于上一个提交点，没有第三种状态。
3. **范围墓碑严格大于才盖**：`range_hidden` 从 `tomb.ver >= rec.ver` 改成 `>`，同版本的写在墓碑之后。

### 10.16 第 9 轮：顺手项 → 掉电护栏（G1）→ 并发护栏（G2）→ 读扩展性（P1）

**顺手项**（都实测）：`del_range` 走 `mem_sorted()` 键序视图找同范围条目（不命中 100k 条 142.8 µs → 摊销 6.43 µs，
第一次要建视图；命中 0.30 µs）；未提交大值 `get` 直接 `get_ovfl_into(out)`（少一次 ≤32 KB 拷贝）；`selcost`/`disc` 并进
`bench6`（`selmem`/`rngmem`/`bigput`）。

**G1 掉电注入 `g6`**（`tests/g6.cpp`）：`VolDev : RamDev`，在第 k 次页写 / sync / 截断处"断电"（已 sync 的页留下，
未 sync 的页随机丢/留半），之后重开、逐键比对**上一个持久提交点**的真值。首跑 4 个种子全红，四个洞见 §12 坑 81~84。
修完 1~44 种子 ×12000 步全绿。代价：每个持久提交点 **2 次 fdatasync**（数据页 → SB），FileDev `fwrite 20000 20 100 0`
0.41 → 0.47 s（≈+70 µs/commit，沙箱 fs；真机 fdatasync 翻倍）。
VolDev 的简化（汇报时注明）：截断调用即持久但"死后"不持久；多页写各页独立丢；快照不跨重开；异步后台写的掉电点归下一 op。
否决了「NOMETASYNC 式」只 sync 一次：第二次 sync 是 SB 持久的必要条件；要省只能连 `promote_pending` 一起推迟（未来项）。

**G2 读写并发 `g7`**（`tests/g7.cpp`）：1 写者 g5 式 op 流 × N 读者 get/select，读者查**不变量**（值 = 键的某个真实版本、
同读者同键 step 单调、select 键严格递增），写者结束后逐键全量比对 + verify + scrub；`make asan` 里再以 TSan 跑三种配置。
首跑抓到坑 85（`scrub()` 不持锁），TSan 再抓 3 类（§12 坑 85）。

**P1 读扩展性（方案 A）**：

* 问题：`bench6 rget {1,2,4} 100000`（10 万键、单 run、全命中缓存）= **96.4 / 109.0 / 171.3 ms** —— 读越多越慢，
  `get` 整段持 `recursive_mutex`。
* 做法：
  1. **锁**：`XLock` = 写独占（可重入，`owner`+`depth`）+ 读共享；`WGuard`（写入口）/`RGuard`（读入口）。
     `RGuard` 在持独占的线程里是空操作；共享读关着 / 账脏 / 没领到线程槽 ⇒ 退化为独占。
  2. **线程槽**：进程级 `TlsIdPool`（32 个槽，先发小号，线程退出归还），Store 按槽存 `Tls`（64 B 对齐）：
     风险指针 `pin`、共享深度 `sdepth`、每线程计数器、私有页缓冲、`read_ovfl` 暂存。计数器 getter 对各槽求和。
  3. **页缓存**：`CacheEnt{atomic pid, buf}`，每组 `CSet{字节自旋锁, MRU 位}`。独占路和以前一样（零原子 RMW）；
     共享路是**风险指针协议**：命中 = 先发布 `pin`（seq_cst）再复核 `pid`；踢页 = 先 `pid.exchange(NIL)` 再扫所有槽的
     `pin`，被钉就换另一路，两路都被钉就读进本线程私有页缓冲（不进缓存）。每线程同时只持一个 `page()` 指针
     （老契约"指针活到下一次 page()"），所以一个 pin 就够。`prefetch` 同协议、不钉；`inval` 只在独占下。
  4. **读者会碰的可变状态**：`Run::meta_pending` 改三态原子（CAS 抢装载，其余自旋等）；`get_at` 问 bloom 前先
     `ensure_meta`（bloom 也在 meta 里）；`ensure_maxhi` 原子脏位 + 小锁；溢出值缓存 `ovc_*` 上 `ovc_mu_`，命中在锁内抄出；
     `mem_sorted()` 上 `msort_mu_`；`scr_busy_` 原子 exchange；`dirty_` 原子；读路径 `runs_[...]` 改 `find`。
  5. **接口**：`set_shared_reads(bool)`，**默认关**。开着时持共享锁的线程再进写入口 ⇒ `RC::BUSY`（不升级：升级间隙里别人
     的维护可能 delete Run ⇒ 游标 UAF）。约束写进注释：开了共享读就**不要在 select/scan 回调里写**。
* 实测（`build/bench6 rget <threads> 100000 4096 [shared]`，2 核沙箱，各 2~3 次）：

| 线程 | 改前（独占） | 改后 `shared=0`（独占老路） | 改后 `shared=1` |
|---|---|---|---|
| 1 | 96.4 ms | 89.3 / 91.7 / 97.3 ms | **87.6 / 91.0 / 94.8 ms** |
| 2 | 109.0 ms | 111.1 ms | **51.8 / 58.8 / 59.7 / 63.5 ms** |
| 4 | 171.3 ms | — | **54.1 / 59.4 / 60.6 / 61.8 ms** |

  验收「2 线程 ≈55~65、4 线程不劣于 2、TSan 干净」三项都到：`tsan_g7` 默认 / `3 6000 4` / `G7_EXCL=1` 均 0 警告。
  单线程开销 +3%（噪声内，上限 10%）。
* **小缓存（64 页，19 万次 pread）不加速**：1/2/4 线程 147 / 169 / 173 ms。去掉设备层原子统计也一样（164 → 159），
  瓶颈是沙箱的 pread 路径不是 Store 的锁 —— 真机预估可扩展，**未实测**。
* 代价：每读者线程 1 页私有缓冲 + ≤32 KB 溢出暂存（堆，首次用才分配）；每个 Store 33 × 64 B 线程槽；
  进程最多 32 个"快路"线程，第 33 个起读也走独占。
* 坑 86（写者饥饿 → 写者优先 → 读者饥饿 → 让一手）见 §12。

**P5 快照期维护放开**：

* 以前 `consolidate / relocate / checkpoint / shrink` 见到 `nsnap_ > 0` 就 `BUSY`（第 6 轮的保守开关），g5 里 35~40%
  的维护调用因此空转；一个长时间持有的快照（备份 / 大 select）期间文件只涨不落、清单链无限长。
* 口径 = `compact_pass` / `retire_dead_runs` 早就在用的 **snap_max**：只动 `ver > 最新快照` 的 run。它们任何视图都看不见、
  任何回退点都不需要，旧页立即可复用（`run_page_safe`）。`ver <= snap_max` 的 run 原地不动：
  合并它们要么丢某个较新快照还看得见的版本（`consolidate_impl` 里残留的 `snap_min()` 就是这种错，只因 BUSY 门槛没出事），
  要么得按"相邻快照区间"分组 + 每组自己的墓碑视图 —— 收益小没做；搬它们是正确的但旧页要 deferred 到快照释放、链不能接管
  只能重写（第 6 轮量到的 1.7×），也不做。
* `checkpoint` / 提交路径的自动全量清单（`MAN_SNAP_AT`）快照期也写：老链页里**快照之后分配的**（`man_new_`，内存集合，
  不改格式）立即回收，其余 deferred。没有这一条时 compact_file 每轮一次 checkpoint，300 轮把高水位推到 19×（snapmaint 实测）。
* `shrink` 快照期砍到 `max(live_top, deferred_ 上界)`：回退点需要的页要么还活着（live_top 算到）要么在 deferred_ 里。
  第一版把 top 钉在每个快照的 `s.tail`，结果快照期一页都收不回来（s2：used 575 / 实际占用 201）；现在回退时
  `tail_` 夹到设备长度即可，不必把文件撑回去。
* 坑 87（`rebuild_free` 把 deferred_/pending_free_ 当空闲页）见 §12。
* 实测（`build/bench6 snapmaint <nkeys> <rounds> [cf]`：持一个快照，每轮整库覆盖 + commit + 维护，最后 rollback 逐键比对）：

| 场景 | 改前 | 改后 |
|---|---|---|
| 2000 键 × 300 轮，`compact_file` | 维护 300 次全 BUSY；高水位 36 → **272 页（7.6×）** | 300 次全 OK；**71 页（2.0×）**；回退 0 错 |
| 20000 键 × 20 轮，`compact_file` | 全 BUSY；334 → 1111（3.3×） | 全 OK；**680（2.0×）** |
| 2000 键 × 300 轮，仅 `consolidate` | 272 | 272（不 shrink 尾部不落；实际占用远小于高水位） |
| g5 维护调用 BUSY 比例 | 35~40% | **0**（1~60 种子、100k 步长跑全绿） |
| s2（每 ~16 步一次维护，快照期一半时间） | 2.8~3.1 s | 3.1~3.5 s（快照期维护真在干活；噪声大） |

* 语义变化（文档明示）：快照期维护返回 OK 但**只收快照之后的垃圾**；老 run 可能钉着尾部，文件长度要等
  `forget_snapshots()` 后的下一次 `compact_file` 才回落到存活集（s2 的回落检查改为先 forget）。

**P3 大值链写异步化**：

* 问题：`put` 一个 > `INLINE_VAL_MAX` 的值会**当场**把溢出链写到设备（2 次写调用），异步模式也不例外 —— run 页早就交给
  IO 线程了，链却还在前台。慢设备（每次写 100 µs）上 8 KB put = 376~399 µs。
* 做法：`write_ovfl(..., bg=true)`（只有 put 路径传 true；归并物化大值仍同步）在 `async_` 下把链拼成和同步路径**字节数相同**
  的两个 IoJob（前 np−1 满页一块、末页按用量）入队，前台只剩分配 + 一次拷贝。三处配套：
  1. `read_ovfl` 是裸读（不经过 `page()`），先 `wait_pages(pg0, npages)`（一次加锁等整条链）；
  2. `free_pages` 先 `wait_pages`：刚 put 的链被覆盖 / abort 时可能还在飞，释放后立刻复用会被排在后面的旧写覆盖
     （两个 IO 线程时连 FIFO 都不保证）；等不到（设备卡死）宁可漏掉这几页，下次挂载 `rebuild_free` 找回来；
  3. 提交点不用改：`commit_delta` 本来就 `wait_io`，链不落地 SB 不写；后台写失败走已有的 `io_err_` 路径（提交失败 → reload）。
* 实测（`build/bench6 bigput 500 8192 100 <io_threads>`，SlowFileDev 每次写睡 100 µs；`bigput 2000 8192 0` 快设备）：

| 场景 | 改前 | 改后 |
|---|---|---|
| 慢设备 8 KB put 前台延迟 | **376~399 µs**，前台写调用 2.0/put | **4.6~6.0 µs**，0/put |
| 慢设备 put+commit 合计，io_threads=1 | 202~210 ms（commit 6~11 ms） | 212 ms（commit 210 ms）—— **只是把延迟从 put 挪到了 commit** |
| 同上，io_threads=2 / 4 | 202 ms（链在前台，多线程无用） | **116 / 58 ms**（链写在 IO 线程间并行，设备得有并行度） |
| 快设备 8 KB put / commit | 7.2~8.5 µs / 18~20 ms | 4.2~4.9 µs / 24~26 ms（合计不变） |
| `bigget 16 20000 8192` 热读 | 4.33 ms | 3.95 ms（`wait_pages` 在没有在飞页时只是一次原子读） |

* 结论要说清：**单 IO 线程下没有吞吐收益**，收益是 put 延迟与"设备并行度 × IO 线程数"；真机 NVMe/eMMC 的并行度未实测。
* 读己之写：put 大值后立刻 get，会等这条链落地（= 一次设备写延迟）。

### 10.17 第 10 轮：R0 悬崖（压实 / 层合并的四处缺陷）→ H0 护栏 → R9

**现象**（`bench/probe/wprof.cpp`，公开 API，`g++ -std=c++17 -O2 -pthread -Iinclude bench/probe/wprof.cpp`）：
2 万键 × 500 B、每次提交覆盖 500 键，前 100 次提交 2~4 ms/次，之后一路涨到 p90 400 ms、max 1 s；
10 万键 × 2000 键/提交时单次提交最长 **17 s**。`gprof` 把 90% 的时间指到 `compact_pass` 里的两处 `count_refs`。

**四层机制**（§12 坑 88~91）：

| 层 | 缺陷 | 后果 |
|---|---|---|
| 坑 88 | `count_refs` O(段² × 单元)，每次提交两遍 | 5500 单元 × 93 段 ⇒ 1.5 s/提交 |
| 坑 89 | 压实产物层号 `best_lvl+1` 无上界 | 逃出 `level_pass` 视野，run 数 → 单元数（685 / 851 条） |
| 坑 90 | 压实产物沿用最新源 seq | **读到过期值**（老引擎 `ovw 5000 500 200 200` 22% 的键） |
| 坑 91 | 快照钉住最老 run，合并组跨过中间 run | **读到过期值**（快照释放后的第一次 L0 合并） |

坑 90/91 是正确性缺陷而不是性能缺陷，而且是第 7 轮以来一直在的；它们没被 34 段测试抓到的原因是
工况（几千个键 × 几百次提交 × 每次几百键覆盖 ⇒ 上千个单元、几十次压实、多级合并）和检查方式（`verify()` 只对结构账，
不对"值是不是最新"）都不对。这一轮的测试补的就是这两点。

**修法**：
1. `Run::refs` O(1) 维护（9 处落点），`verify()` 慢路交叉核对；
2. 压实产物 **seq = `finish_run` 分配的新鲜号，层号 0**；`apply_man` 把老库 5/6/7 层夹回顶层；
3. `level_pass` 显式检查合并组在全库 seq 顺序上连续（`gap_between`），在夹缝处截断；最老那条被隔开就提升一层（内存层号）；
4. R9：`split_pass` 一次扫描收齐候选，不再每切一刀扫一遍 `cells_`；
5. 新公开调试 API `lvl_hist()`、`max_segs_per_cell()`。

**数字**（沙箱，同时段各 3 次，取中位；`/tmp/wprof_old` = 改前头文件编的同一探针）：

| 工况 | 改前 | 改后 | 复现 |
|---|---|---|---|
| 2 万键 × 500 B，200 次 × 500 键 | avg **100.3** ms / p90 395 / max 993 ms，>50 ms 61 次，runs **685**，used 12805 | avg **7.9** ms / p90 27.0 / max 95.6 ms，>50 ms 3 次，runs **19**，used 9750 | `wprof 20000 500 200 500` |
| 同上 320 次 | avg 165.2 / p50 63.8 / max 977 ms，>50 ms 167 次，runs 851 | avg 10.1 / p50 2.5 / max 129.6 ms，>50 ms 8 次，runs 28 | `wprof 20000 500 320 500` |
| 10 万键 × 500 B，150 次 × 2000 键 | avg **407** ms / p90 548 / max **17.3 s**，runs 92（5506 单元，≈93 段/单元） | avg **37.0** ms / p90 96 / max **593 ms**，runs 11 | `wprof 100000 500 150 2000` |
| 覆盖风暴写放大 / 空间 | 2.68× / used:live 1.58× | 2.68× / **1.27×** | `bench6 ovw 20000 500 200 500 0` |
| bench3r 写放大 200k/2000 | 2.77× | 2.77×（这条负载不压实，预期不变） | `bench3r 200000 2000` |

残余：改后的 max（96 / 130 / 593 ms）全是层合并级联（一次 L0→L1 合并 8~32 条 run 同步做完），
是 R2「合并预算 + 维护分步」的对象，不在 R0 范围。
一个新的取舍：压实产物进 L0 且 100% 存活，会把 L0 的"垃圾占比 ≥ 30% 才合并"条件稀释，L0 更容易攒到 32 条
再一次性合并（10 万键工况 max 从中间版本的 493 ms 变成 593 ms 就是这个）；R2 做分步之后这一下会被切开。

**H0 护栏**：`bench6 ovw <keys> <vb> <commits> <per> [every]`（每 every 次提交打印 runs / cells / 最大段数 / 层级直方图 /
used / live / 区间 max；末尾逐键回读、verify、设备写放大）和 `tests/g8.cpp`（见 §12 坑 91 的教训）。
g8 对老头文件编译：seed 1 第 51 次提交、seed 2 第 18 次提交就报过期值；关掉连续性检查：3 个种子都在第 18 次提交报。

### 10.18 第 11 轮：坑 92~95 → R1+R10 → 坑 94 → R2 → H1/H2/H4/H5 → R7/R8/H3（R3 只出设计，P2 单开）

讨论稿在 `backup/r18/swept/docs-hist/DISCUSS11.md`（四个坑的最小复现、gprof 剖面）；R3 设计稿在 `backup/r18/swept/docs-hist/DISCUSS12_R3.md`。本轮全部步骤都带

新测试段自带 `alarm()` / 步数上界。

**步 0：三个老坑的修法**（§12 坑 92/93/95；`tests/g9.cpp` t92/t93/t95）
- 坑 93：`add_tomb` 的同 lo 支配规则只在**无快照**时删旧墓碑；快照期并存，`forget_snapshots` 时 `prune_tombs()` 补剪。
- 坑 92：`exact_live_recs` 只扫本 run **仍被引用的段的页**（悬空记录天然不算）；`retire_dead_runs` 的校准成本 ∝ 引用页数。
- 坑 95(b)：存活账口径统一为「赢家就算活，不看 blen」（`probe_prev` / `merge_emit` / `exact_live_recs` 去掉 `blen &&`），
  和 `settle_ranges` 整盖快路径一致。

**R1 合并账目增量化**（`merge_run_set`）：以前合并完对每个触及单元 `recount`（k 路归并单元内**全部**段；100k×500B
负载 18 次合并 ⇒ 82k 次 recount，`merge_emit<recount>` 占主线程 CPU 29%）。现在归并流里顺手记账：键序递增 ⇒ 单元指针
单调前进；每条 emit 的记录知道所属单元、来源 run、页上字节、来源 run 在该单元有没有段（没有 ⇒ 以前不可见、不在 `c->live`
里）、是否可能被更新的 run 盖住（布隆候选，产物落地后 `newer_has` 精确确认）。于是
`新段 live = emit 数 − 被盖数`，`c->live = c->live − 以前可见的源赢家字节 + (新段全部字节 − 被盖记录的新字节)`，

新增的五条不变量（这一轮之后，破坏它们任意一条都会在测试里直接炸）：

1. **页号 32 位，`sp` 先打包后放宽**：`sp_pack(页, 偏移)` 用 `SP_SHIFT=12`，
   任何 `<<16`/`&0xFFFF` 出现在页号路径上都是 bug。
2. **`len == OVFL_MARK` ⇒ 记录体恰好 16 B**：`rec_size()` / `pg_rec_size()` /
   `close_page()` 的重排 / 游标推进 / `verify` 五处必须给同一个答案
   （少改一处就是"页内记录错位"，而 CRC 是对的，只能靠有序性和回读抓）。
3. **溢出链是普通页**：`rebuild_free()` 必须把它算进"已用"（否则挂载后会被二次分配），
   run 被摘链时必须 `free_ovfl_of()`（否则泄漏到下次挂载）。
4. **范围墓碑只活在清单里**：不进键空间 ⇒ 扫描/游标/flush 全都不需要特判；
   `get` / `Cursor::next` / 归并三处各看一眼 `range_hidden()`；墓碑版本 ≥ 记录版本才盖住。
5. **`page()` 的指针只活到下一次 `page()`**：任何在遍历页的过程里读**别的页**
   （溢出链、meta、清单）的代码，都必须先把需要的字节拷出来 —— `verify` 里踩过（§12 之 40）。
`f4`/`q1` 在每轮改写后都断言 `verify` 零错误 —— 记账漂移会在测试里直接炸，而不是
等到线上"空间莫名虚高"。

**介质校验 `scrub()`（缺口 ③）**：`verify()` 走页缓存（它要检查的是"逻辑账对不对"），
`scrub()` **绕过缓存、直接 `dev->read` 每一页**再按页头 CRC 校验 —— 缓存里的页是新写进去的，
检验它等于检验自己（第一版就是这么写的，翻转一位完全抓不到）。单副本没有冗余可修，
它的价值是"在错误传播之前发现"：返回 `RC::CORRUPT` + `bad` 页数 + 第一个坏页号，
并且**重开后仍能报出同一页**（错误在介质上，不在内存里）。`tests/c1.cpp` 守着这条。

## 12. 这一版踩过的坑（都写进了不变量）

1. **幽灵段**：切分后给子 cell 保留"该 run 在本区间没有记录"的段，日后合并回来会重复计入。
   → 段必须带键域，且键域非空才保留。
2. **cell 回并**会把邻居的记录重新纳入视野，与压实段形成重复副本。→ cell 只细分不回并。
3. **压实产物的 seq 必须落在"栈底"且全局唯一**，否则会和被它替换的 run 撞号，
   seg map 里一条覆盖另一条，读到的就是旧值。
4. **页号会复用**，所以段身份 = `(cell, rid, seq)`，清单里的 `M_SEG_DEL` 必须带 seq。
   （这一条在组提交/分层合并引入后**再次咬人**：重放时 `M_SEG_DEL` 删掉了刚复用同一
   页号的新 run。）
5. **提交失败前不能复用刚释放的页**（否则崩溃后"完整旧态"已被破坏）→ `pending_free_`。
6. **NOR 只能 1→0**：先擦后写，且擦除必须发生在提交点之后。
7. **压缩产物与快照互斥**：有快照时暂停回收。
8. **压实只保留最新版本**——所以"前缀合并"永远回收不了空间，必须整 cell 重写。
9. **分层合并的产物必须继承"源里最新的 seq"**，否则旧值复活（见 §5.3）；合并组还必须在全库 seq 顺序上连续（坑 91）。
   **单元压实产物**则取新鲜 seq、进 L0（坑 90）。
10. **分层合并时不要递减源 run 的存活账**，否则活着的 tombstone 会被当成垃圾回收掉。
11. **记录头改窄必须一次改全**：16 B → 10 B 时有 4 处 `off + 16 <= used` 漏改，
    表现为"提交后 get 不到"。改完要 `grep '16 <= used'` 与 `, 16)`。
12. **部分页写必须 4 B 对齐**：`RamDev::valid` 要求 `off%4==0 && len%4==0`，
    否则整次提交返回 `RC::IO`。
13. **游标跨版本要按 run 的 ver 过滤**；记录版本已经不在记录头里了。
14. **异步写的页在提交点之前不能复用**：`commit(false)` 已经把页交给后台线程，
    但清单还在旧状态上；若此时 `free_page` 让它被重新分配，后台线程会把新内容写到
    "还挂在旧清单上"的页 → 崩溃后旧态也坏了。异步 flush 因此**只做 flush**，
    回收/合并一律留到提交点（`pending_free_` 之后才 promote）。
15. **记账只能有一条算术**：`live/dead/pages` 由 `recount(cell)` 从段集合直接算出，
    结构性改写（挂段、摘段、升层、压缩、分裂）之后统一重算。散在五六个地方的增量补丁
    漏一处就是一次"live 漂移"——现象是 cell 该分裂不分裂、空间虚高、压实选错受害者，
    而且 `verify` 一开始查不出来（因为两边用的是同一份错账）。
16. **胜者规则只能有一条**：可见版本最大者胜，同版本 seq 新者胜。段在 cell 里的排列
    只表示归属；按"段的先后"读会在"低 seq + 高版本"的合并产物上读到旧值。
17. **收缩会被清单卡住**：数据都搬到低处了，高水位还是下不来 —— 清单链的页是当年
    随手分配的，飘在高处。必须先 `checkpoint()` 重写清单，`shrink()` 才有意义。
18. **空闲表要按地址索引**：原来是 `multimap<长度, 起始页>`（按大小最优适配），
    搬家/收缩恰恰要"最低地址"，于是改成 `map<起始页, 页数>`：低地址优先分配、
    邻居合并只需看一眼后继。同一个数据结构，两个用途。
19. **异步写的收益不在吞吐峰值，而在停顿分布**：页写本来就是一个批次一次顺序写，
    前台 CPU 才是瓶颈；把 I/O 挪到后台换到的是"工作区 8.4 MB → 2.8 MB"和更平缓的停顿，
    吞吐只能做到持平（4.3 vs 4.1 µs/op）。**落盘粒度必须按字节而不是按提交**：每 8192 条
    落一段就是 24 条与全键域重叠的 run，实测反而慢 2.3 倍（4.6 → 10.7 µs/op）。
20. **切分单元必须同时收紧页区间**：`split()` 只改键域不动页区间（零数据搬移），
    但页区间不收窄的话，每个单元都要从 run 的首页开始扫 —— 单元数 × 页数，四舍五入就是
    O(n²)。实测 30k 条全扫：698 → 68 ns/条（10×），一次 50k 提交 195 → 22.6 ms（8.6×），
    `verify` 74 → 6.5 ms。**这是本轮最大的一个 bug**，而它不违反任何不变量，只是慢。
21. **CRC 要走硬件**：查表实现 374 MB/s，一页 4 KB 是 11 µs；x86 的 `crc32` 指令 7.5 GB/s，
    一页 0.6 µs。每页一次校验，这条差 20 倍，直接决定 verify/mount/每次提交的常数项。

22. **`truncate()` 只能减不能增 = 一次性的永久封顶**：`shrink()` 之后设备就再也长不回去，
    库会在某天写到 `NOSPACE` 之后**永远**写不进（连删都删不掉，因为删除也要落页）。
    修法：`BlockDev::max_pages` 记设备上限，逻辑容量取上限、物理长度单独记，
    分配时按需 `truncate()` 增长。
23. **满库必须"删得掉"**：只给用户 7/8 的容量还不够 —— 一批全是覆盖/删除的写不增长存活集，
    必须允许它动用预留区。否则"满了 → 要删 → 删也要空间 → 还是满"死锁。
    判据是"新字节 ≤ 被替换字节"（`flush_mem` 里一次 `probe_prev` 求和即可）。
24. **维护不能把提交搞失败**：压实/合并/清单页都是机会性的，拿不到空间就跳过本轮。
    旧实现里 `merge_run_set` 一次 `NOSPACE` 就把整个用户提交带崩，用户看到的是
    "库满了"，实际上是内存里的垃圾没地方腾。
25. **异步在飞时重建状态 = 用旧页覆盖新页**：`rollback()`/`reload()` 不 `wait_io()` 的话，
    worker 手里还握着旧分支的页，写下去正好落进刚回收重分配的位置。
    症状是**随机坏清单项**（`npages` 变成天文数字），追了整整一轮。规矩：
    **任何"按盘重建内存"之前，先把在飞的 I/O 等干净**。
26. **清单项必须自证清白**：`apply_man` 里照着 `m.npages` 分配就是给了坏数据一个
    申请 9 GB 内存的机会。越界条目一律丢弃 + 计数，挂载永远不会因为一条坏记录失败。
27. **"脏不脏"要用精确账，不能用保守估计**：`run->live_bytes` 是合并时用布隆算的
    **上界**（只会多算），拿它判断"这条 run 值不值得重写"，结果垃圾越多越不肯重写，
    空间放大卡在 3× 不动。改成 `Σ cell->live`（精确、`verify` 每轮都核对）。
28. **`compact_file` 要归一两次**：第一次归一时旧段还占着低位，合并出来的 run 只能落在
    高处；收完一遍之后再归一次，低位全空 ⇒ 一条 run 能整块搬到最前面。
    一次归一时 `used` 停在 3×live，两次之后 `used ≈ live + 4` 页。

29. **页缓存是直映的，"页指针"活不过一次 `page()` 调用**：`page(pid)` 把要读的页拷进
    `cache_[pid % N]` 的缓冲并返回它的首地址。若在遍历某一页的过程中再读别的页，
    手里那个指针会**原地变成另一页的内容**。`replay_manifest` 就是这么在清单页里
    "读到一条来自数据页的记录"的（随机坏清单项的真凶）；`exact_live_recs` 也踩了同一个坑
    （存活数恒为 0）。规矩：**跨页操作必须先把当前页拷出来**。
30. **64 位哈希被截成 32 位 ⇒ Bloom 恒假**：`Bloom::add` 用完整 64 位哈希落 4 个位，
    查询侧却写成 `u32 hk = khash(k)`，于是 `may()` 几乎总是 false。后果不是"读错数据"，
    而是**存活账永远算满**：零写回收从不触发、分层合并觉得"没垃圾不用合并"，
    run 越堆越多、读页从 8 万涨到 20 万、同一负载 0.95 s → 16.29 s（17×）。
    教训：**布隆是"保守过滤器"，它的错误方向只会让最优路径失效，不会报错** ——
    所以存活账必须在回收前用精确复核兜底（见 31）。
31. **回收前必须精确复核**：`retire_dead_runs` 判"整条 run 全死"时，不能只听增量计数，
    要 `exact_live_recs()` 扫一遍确认。计数是提示值（只会偏低），复核把"误删活数据"这条
    最可怕的路彻底堵死，代价是每轮多扫一遍待回收的 run。
32. **回退必须让逻辑时钟继续前进**：`rollback` 把 `vers_` 恢复到快照点，另一个超级块槽里
    "版本更高的旧分支"就会在下次挂载时胜出 —— 回退被静默复活。现在是
    `vers_ = 回退前的时钟 + 1`：回退的是**状态**，不是历史。`r2` 阶段 4 守着这条。
33. **回退要一起还原回收账**：`pending_free_`/`deferred_` 里装的是"还没归位"的页。
    不还原，回退后它们会被 `promote_pending()` 放进空闲表 —— 而那些页属于被回退掉的分支，
    于是同一页被分配两次。快照现在把它们整体存下来，回退时按内容还原。
34. **合并产物的存活账不能"事后按自己的 seq 反推"**：合并后的 run 只有一个 seq（= 源里
    最新的那个），拿它去问"这条记录有没有更新副本"会把从旧源搬来的记录算成新的。实测热点
    覆盖负载里一条 run 记 118 条活、真值 40 ⇒ 永远不满足"全死可回收"，空间只涨不降。
    → 判据必须用**产物自己的段身份 `(seq, page0)`**，而且要等 `finish_run` 分配完页号
    之后再判（`(seq,rid)` 才是读路径的全序）。
35. **切分/摘段时段的存活计数要"退回"**：段级记账里 `run->live_recs` 是它在所有单元里的
    `live` 之和。切分用 `segs.swap()` 换掉整张表，原 `Seg` 对象连同计数一起被丢掉；不先
    `seg_set_live(sg, 0)` 退回，随后两次 `recount`（父子各一次）就会把同一批记录加两遍 ——
    现象是 `live_recs` 恰好是 nrec 的 2 倍，`verify` 的 `run live recs` 直接报错。
36. **压实产物的 seq 要在"删除源 run 之前"取**：`compact_cell` 原来在释放源 run 之后才去
    `runs_` 里找它们的 seq/lvl，删掉的自然找不到，于是拿到的是一条无关 run 的 seq ——
    产物和一条还活着的 run 撞号，`(seq,rid)` 的胜负随手一翻就变，账跟着漂。
    （第 10 轮后此坑成为历史：产物不再沿用源的 seq，见坑 90。）

37. **`sp.packed` 的截断是静默的**：`packed = 页<<16|偏移` 在页号 >65535 时把页号截成
    余数 —— 不报错、不崩，只是**读错了页**。所以容量改造的顺序不能反：先改打包
    （`页<<12|偏移`，20 位页号），再放宽 `PageId`。反过来做的话，中间态的库看上去
    一切正常，只是超过 65535 页之后开始返回别的键的值。
38. **`PageId=uint16_t` 还会污染"设备容量"这个入参**：`RamDev(200000)` 被隐式截成
    `200000&0xFFFF = 3392` 页，`RamDev(65536)` 直接截成 0 页。调试时这个现象会被
    误判成"元数据页把设备占满了"（当年就是这么走的弯路）。**任何"页数"参数都必须先
    确认类型够宽**，别等写到一半才 `NOSPACE`。
39. **`heal_missing_meta` 不能边遍历边 `runs_.erase`**：第一遍收集候选时顺手 `erase`，
    第二遍 `begin()` 会用到已经失效的 `end()` 快照，于是**一个候选都跳过**
    （现象：`heal` 返回 0，看起来像"没找到需要补的 run"）。必须先收集 `page0` 列表再循环。
40. **`read_ovfl` 会踢掉页缓存，遍历中拿着的 `p` 立刻失效**：`verify` 原来在"逐页解析记录"
    的循环里直接调 `read_ovfl`，之后继续用同一个 `p` 往下走 → 读到的是**溢出页的内容被当成
    数据页**，`recs` 从 2000 变成 2918、报 `run unsorted`。正确写法：先把 16 B 描述符
    `memcpy` 到局部，读完链再 `p = page(run->page0 + i)` 重新定位。这就是"页指针只活到
    下一次 `page()`"的第 N 次咬人。
41. **`std::map::erase(it)` 之后不能再用 `it->second`**：`heal_missing_meta` 里
    `free_.erase(it); if (it->second > mn) ...` 是 use-after-free（ASan 直接抓到，
    普通构建下只是"偶尔算出个荒唐的剩余块长度"）。先存 `u32 blk = it->second;` 再 erase。
42. **memtable 里的大值必须**只**落一次链**：`put_raw` 已经写好了链并留下 16 B 描述符，
    `flush_mem` 若再走 `w.add()`（按值长度判断）就会**再写一条链**，而描述符里的那条成了孤儿。
    → `Rec` 加 `bool ovfl`，flush 时走 `add_desc()`（所有权转移，不再复制值）。
43. **`del_range` 只改内存时会被"空提交"快路径吞掉**：`commit()` 里
    `if (delta.empty() && pend_ranges_.empty())` 才是真的没事；原来只判 `delta.empty()`，
    于是"只删了一个范围"的提交被当成"没东西可提交"，墓碑永远不落盘（重开后全部复活）。
44. **全量清单快照会重放超级块里的内联增量**：`write_man_snapshot()` 之后没清 `pend_`，
    而 SB 里的内联增量是在清单链**之后**应用的 —— `M_RUN_ADD` 重放无害，`M_RANGE`
    重放会把刚清掉的墓碑**复活**。→ 快照写完先 `pend_.clear()` 再 `write_sb()`。
45. **溢出链的空间也要在"全死可回收"里算**：摘 run 只 `free_pages(page0, npages+mnpg)`
    会把链落成孤儿（`verify` 干净，但 `used` 只涨不降）。→ 摘链前 `free_ovfl_of(r)`；
    挂载时 `rebuild_free()` 也要把活 run 的链算作已用，否则会被二次分配。
46. **写失败要把已经分配的链还回去**：`RunWriter` 逐条 `w.add()`，第 k 条 `NOSPACE` 时
    前 k-1 条链已经落盘，但 run 没建成 ⇒ 没有清单项引用它们。→ `RunWriter::chains`
    记着本次写过的链，失败路径 `abandon()` 全退。否则要靠下次挂载的 `rebuild_free()` 兜底
    （能兜住，但那段时间的盘是白占的）。
47. **`throw` 不出细节，`assert` 只在 debug**：溢出值的所有边界（3000/3001/4080/8160）
    都必须有测试，否则"恰好跨页"这种 off-by-one 会一路带到线上。

---

48. **快照判据的方向**：`snap_min` 是"最老"，可快照视图要看的是 `ver <= 快照版本`，
    所以"老快照还需要的版本"上界是**最年轻**的快照 ⇒ 判别式必须是 `snap_max()`。
    写成 `min` 的后果不是"慢"，是**较新快照整段丢版本**（s4 的 B 视图 2000/2000 错）。
49. **`clear_state()` 不清 `ranges_/pend_ranges_`**：回退（rollback）后墓碑还在，
    于是"删掉的范围"继续遮蔽回退之后重新写进去的数据。回退必须把范围墓碑一起回到当时。
50. **`forget_snapshots()` 不能"直接把页塞回空闲表"**：它原来无锁、且用
    `free_[p0] = n` 覆盖，和现有空闲块重叠时会**重复计数**（空闲页比实际多，分配器
    发出两张票）。正确顺序：跳过 `>= tail_`、先 `carve_free()` 从现有块里挖掉、
    再插入、最后 `coalesce()`。
51. **链的所有权是"按 run"记的，不是"按页"**：接管链之前必须确认源 run **这次一定死**
    （`take_set_`：`compact_cell` 里是 `count_refs(rid) <= 1`，`merge_run_set` 里是全部 src）。
    只看 `nsnap_==0` 就接管，会让"同一次压实里还活着的另一条 run"的链被转走。
52. **"摘链"之后不能用"表空"当"还没建表"**：`chain_taken()` 把 `ovfl_loc` 清空，
    而 `ensure_ovfl_loc()` 原来的守卫是 `!ovfl_loc.empty()` ⇒ 摘完立刻**重扫数据页**，
    把刚交出去的链又找回来，接着当自己的还掉。表现是 `compact_file()` 之后
    `verify` 报 `ovfl data`（链被后续分配覆写）。修法：`Run::loc_ready` 一次性标志，
    空表也算"建过了"。
53. **接管的链归接管者所有**：`RunWriter::add_take()` 只把描述符写进页，链记在
    `w.takes` 里；`finish_run` 把它记进 `ovfl_ref` 就再也不释放 ⇒ 每压实一次漏一份大值。
    正确做法：`own_chains` 里同时收 `w.chains` 与 `w.takes`（所有权已经转过来），
    `collect_ovfl()` 不再按 `ovfl_ref` 排除。
54. **只算账的遍历不该读大值**：`recount` / `verify` / `check_liveness` 走 `merge_emit`
    时传 `need_vals=false`，否则压实会把每个大值读两遍（`bench5 consol`：读页 2004 → 4，
    接管之后连一遍都不用读）。
55. **"物化过的值"和"接管来的描述符"只能二选一**：`merge_emit` 原来按 `is_ovfl` 交描述符，
    可"没接管"时值已经被读成字节了——回调仍然 `add_take`，新 run 把**不属于自己**的链
    记进 `ovfl_ref`，源 run 接着把链还了。表现同上（`compact_file` 后 `ovfl data`）。
    修法：单独一个 `took` 布尔，只有真接管才交 `dsc`。
56. **`read_ovfl` 会踢页缓存**：`verify`/`scrub` 里"读描述符 → 读链 → 再用原页指针"
    必须重新取页（先把 16 B 拷出来）。这条在坑 40 记过一次，本轮在 `scrub` 里又踩了一次。
57. **`live_top()` 必须把溢出链算进来**：`shrink()` 用它做截断点，漏了链就会把高水位
    截到链中间——下一次写入压在链上，数据**静默消失**（不是 CRC 错，是读出别人的数据）。
59. **范围墓碑的读路径不能是 O(墓碑数)**：`ranges_` 按 `lo` 有序，`hi` 无序，
    一个个往回走就是"几千个墓碑 × 每次点查"。每条目多存 8 B 的**前缀最大 hi**，
    一旦 `maxhi <= k` 立刻停（`g2`：5000 墓碑下 0.25 µs/次）。
    这份前缀和还要**按需**算：每次插入都全量重算是 O(n²)（5000 个墓碑插入 54 ms → 4 ms）。
60. **逻辑删除不改存活账**：`del_range` 一个字节都没重写，但一批记录"变成不可见"了。
    不 `recount` 的话 `cell->live` 与 `verify` 的口径立刻分家（`live mismatch`），
    这些单元还永远不会被当成有垃圾。重算要**先收集受影响的 cell 再统一重算**：
    5000 个墓碑 × 逐个 recount 是 O(n²)（实测 66 ms → 496 ms）。
61. **`compact_file()` 对大值库不保证"变小"**：run 块要连续、链只能随它所在的 run 搬
    （描述符在数据页里），所以 66000×3900 B 这种库归一之后 `96905 → 127795` 页
    （**+31%**），活页 96901。这是"显式维护调用的最坏情况"，不是数据出错；
    断言写成 `used <= live + live/2 + 64`，并在 §14 第 5 条记下真正解法（链的引用计数）。
    **第 7 轮（M1）已解**，而且没用引用计数：根因不是"链被共享"，而是 `relocate()`/`consolidate`
    把链**全部接管** ⇒ 链永远不动、`shrink()` 截不到。解法是 `compact_file` 第二遍只物化
    "末页 > `take_limit_`（= 活页 + 32）"的链（新链经 `alloc_pages` 落到低位的洞里），其余照旧接管。
    `cfcurve`：ratio 1.31 → **1.01**；`b1`：+31% → **+0.8%**（§10.14）。
62. **同 `lo` 的范围墓碑不能互相顶替**：`ranges_` 原来按 `lo` 做键，`del_range(10,90)` 之后
    `del_range(10,20)` 把宽的那条**换掉** ⇒ 21..89 复活。键改成 `(lo, ver)`，插入走 `add_tomb`。
63. **任何判"死/活"的路径都必须同时看范围墓碑**（这是 L4 最大的教训，三处各踩一次）：
    (a) `exact_live_recs`/`retire_dead_runs` 只看"有没有更新版本" ⇒ 被整条盖住的 run 永远
    `live=nrec`、永不退休，而且每次提交都被"校准"重扫一遍（`delloop`：runs 20→138、del 提交 2→68 ms）；
    修法 `run_fully_hidden()`（整条 run 的键域被同一条 `ver >= run.ver` 的墓碑盖住 ⇒ 一页不读）
    + 逐条 `range_hidden`。(b) `probe_prev` 命中旧版本却不看墓碑 ⇒ `flush_mem` 二次扣减。
    (c) 墓碑原来在 `commit_delta` 才落账 ⇒ 被盖 run 要**晚一次提交**才退休；`apply_ranges(delta)`
    提前到 `rebalance` 之前。
64. **未提交的大值 `get` 返回了 16 B 描述符**：`MemTable` 里溢出条目存的是描述符（len=16），
    `get_at` 原样抄给了调用方。修法：`desc_of` + `read_ovfl`。
65. **结构化整数键别用乘法散列的高位做小表索引**：L2 的 ghost 表初版用乘法散列高 8 位映射 256 槽，
    链首页等差（步长 377）两两碰撞 ⇒ `bigget 16` 命中率 0、pread 仍 15008。改 `khash(pg0) & 1023`。
66. **归并物化不能走读缓存**：`merge_emit` 读大值走 `read_ovfl(cacheable=true)` 会把冷扫描的
    ~40% 链灌进 ghost 表、误准入 ⇒ 冷读 +8~10%。`Cur::val(..., cacheable=false)`。
    同理 `verify`/`scrub` 也不缓存（它们要看介质）。
67. **预取绕过了 `wait_page`**（第 5 轮 B2 埋的雷）：`prefetch()` 直接 `read_multi` 落盘字节填页缓存。
    `commit(false)` 刚把 run 交给后台线程、立刻 `select` ⇒ 预取读到的是该位置**上一任**的旧页/零页，
    却以"有效缓存"身份留下；随后 `page()` 等写落地后**命中缓存**返回旧页。`g4` 第 1 段用慢写设备
    把窗口放大：旧版 `select` 只回 **80/3000** 行、之后 `get` 坏 1610 个键、`verify` 报 `page kind`。
    修法：在飞的页一律不预取（截到第一张在飞页为止）；`scrub`/`raw_dump` 裸读前 `wait_io()`。
68. **"已落页、未入账"的 run 必须先于引用它的 DEL 入账**：`commit(false)` 刷出的 run 的 `M_RUN_ADD`
    暂存在 `pend_delta_`，只有 durable `commit()` 会并入清单；而 `consolidate`/`relocate`/`checkpoint`/
    层合并直接走 `commit_delta`，先把那条 run **合并掉（DEL 入账）**，下一次 `commit()` 才把过期的 ADD
    追加进去 ⇒ 重放（回退/重开）复活一条指向**已释放页**的僵尸 run。s2 长跑里它表现为两种面孔：
    僵尸 run 与清单页/另一条 run 共用页 ⇒ 双重释放 ⇒ 两条活 run 重叠 ⇒ **丢 14 个键**（op 7310）；
    僵尸的页后来被 meta 页覆盖 ⇒ 回退 `CORRUPT`、**库被清空**（op 14599）。
    修法：`commit_delta` 统一先并入 `pend_delta_`；`write_man_snapshot` 清 `pend_delta_`
    （全量快照来自内存 `runs_`，已含这些 run）。`commit()` 的"没事可做"早退也要看 `pend_delta_`。
69. **快照点必须是一个提交点**：`snapshot()` 只抓 `pend_`，不抓 `pend_delta_`、也不抓 `mem_` 里的
    逻辑提交 ⇒ `commit(false)` 之后立刻 `snapshot()`，回退会把这些**已对读者可见**的写丢掉。
    现在 `snapshot()` 先 `commit()` 再抓（语义：快照 = 持久提交点；没东西可提交时是空操作）。
70. **压实搬家的两个布局坑**：(a) `relocate()` 判"有更低的洞"用的是 `npages`，不是 `run_block`
    （数据 + meta + 附件）⇒ 洞装不下整块，搬家又落回尾部，白写一遍。(b) run 搬到低位后，`checkpoint`
    的新清单页按"最低空闲页"分配，正好卡进低位大洞 ⇒ 洞 = 块 − 1 页，之后每一遍都搬不下去
    （s2：used 386 vs live 184）。修法：`compact_file` 期间清单页放到**最高 run 块之上**
    （`man_high_` / `alloc_man_page`），收尾时若清单页还能更低就再写一次（1 页 + SB）。
    `g4` 第 4 段：6 轮搬家后 `used == live`、0 个空闲碎片。
71. **洞比块小一点时的"弹跳"**：b1 的洞 30155 页就在 30890 页的 run 块正下方 —— 直接搬搬不下去，
    但强制重写一次会先落到尾部、再由 `relocate` 落进合并后的大洞（2 次重写换回整个洞）。
    无条件 force 在小库上是纯浪费（s2 写页 +23%），所以判据是 `bounce_gain() >= 32 && >= 块/8`
    或 `chain_top() > take_limit_`。代价：compact_file 密集的 s2 无回退长跑写页 +7%。
72. **测试方法论：回退后"resync 真值"等于没测**。s2 以前每次 `rollback` 后用 `get` 重建真值再往下跑，
    坑 67/68/69 全在它眼皮底下跑了两轮。现在 `snapshot()` 时存一份真值，回退后**逐键比对**；
    `make test` 每一段"回退/重开后对拍"的都应如此。
73. **大值覆盖/删除漏链**（A2 第一次跑就抓到）：同一批里把大值覆盖成别的值 / `del` 掉，`mem_` 里 16 B 描述符
    被覆盖，链既不属于任何 run、也不在空闲表 —— 进程活着就一直漏，重开后 `rebuild_free` 才收回。
    修法 `drop_mem_chain`（`free_pages(..., snap_safe=true)`：链写在上个提交点之后，没有快照能引用它）。
    B3 的分配规则在这之后还试了三版才定：① 最低空闲页 ⇒ `compact_file` 的清单页卡进低位洞（坑 70）；
    ② 最高活 run 块之上 ⇒ 平时也抬高水位；③ 纯大小规则 ⇒ 搬家期清单页仍挡路；④ 定稿 = 平时大小规则 +
    搬家期位置规则（`man_high_`）。
74. **`shrink()` 截断未提交大值的链**（g5 seed 1 第 303 步）：大值在 `put` 时就落成链，只有内存表的描述符引用它，
    `live_top()`/`rebuild_free()` 只看 run 和清单 ⇒ `SHRINK tail 37 -> 34` 把链截掉、下一次分配盖住它，
    提交后 run 的描述符指向别人的页（`get` NOTFOUND）。修法：`for_each_mem_chain` 进 `live_top`/`rebuild_free`/
    `ownership_check`（所有者 kind 7）。规则：**新的页引用来源必须同步这三处**（旧规则只说"新页类型"）。
75. **`del_range` 之后同批的 `put` 丢失**：墓碑版本取提交版本，和同一次 flush 出来的 run 版本相等，
    `>=` 规则把 del_range **之后**写的键一起盖掉（`del_range(1,10); put(5); commit(); get(5)` → NOTFOUND）。
    修法：墓碑版本定在**发出时刻**的 `open_vers()`（`PendRange{lo,hi,ver}` 带进清单），`range_hidden` 改成
    严格 `>`；`run_fully_hidden`/`settle_ranges` 快路径同步（单元里有 run 版本 ≥ 墓碑版本就老老实实 recount）。
76. **`del_range` 提交前对 `get` 不可见**：以前只进 `pend_ranges_`。现在 `del_range` 立即 `add_tomb` 进 `ranges_`，
    内存表里已有的同范围条目就地改成点墓碑（它们比墓碑早，且 `get`/游标的内存表路径不查范围墓碑）；
    存活账**攒到**提交/`verify` 时一起结（`settle_ranges`，`PendRange.acct`），否则 5000 条墓碑 × 单元的逐条
    recount 又回到 66 → 496 ms 那条老路。`abort()` 要撤掉这些墓碑只能 `reload()`（`add_tomb` 会吃掉被支配的旧条目，
    不可逆）。
77. **`select`/`count`/`scan` 不读内存表**：`get` 看得见未提交的 put/del，`select` 看不见，直到数据进 run
    （同步模式下连 `commit(false)` 之后都看不见）。`Cursor::next` 现在多归并一路内存表（同键内存表赢、墓碑不吐、
    未提交大值物化到游标缓冲、`view` 过滤）；`scan` 改走游标并加锁。键序视图 `mem_sorted()`：按 `MemTable::gen()`
    缓存，`epoch`（clear 计数）不变且条目只追加时只排新尾巴再 `inplace_merge` —— 第一版全量重排在 g5 的
    写/查交错下 100k 条要 6 ms/次，增量后 0.06 ms；中间还踩了一脚：没看 epoch，clear 之后长度又长回去就把
    新条目当成旧前缀（g5 八个种子全红）。
78. **维护操作把未提交的范围墓碑"半持久化"**：坑 76 让墓碑立即生效之后，`compact_file` 的归并把被盖住的记录丢了，
    墓碑本身却没进清单 ⇒ 重开后是"部分删除"，既不是上个提交点也不是现在（g5：352 个键缺失的前身）。
    两条路：维护只看已提交的墓碑（要把"已提交视图"穿过 merge/retire/recount 全部路径），或**维护先提交**。
    选了后者（`maint_commit`：有未提交的写才真提交），顺手把 L2 的残留「consolidate 不先 flush mem」也关了。
    代价：维护极密的 s2 CPU +20%（§10.15）。
79. **范围墓碑下的点墓碑，两套口径**：`merge_emit`/`verify` 从不把点墓碑算作被范围墓碑盖住（`blen &&`），
    它的字节一直记在 live；`probe_prev`/`exact_live_recs` 按"被盖"算 ⇒ 覆盖这种键时少扣一次，**账差 4 B/条**
    （g5 seed 7：`live mismatch` 24046 vs 24050，`FCS_VERIFY_DBG=1` 逐条对出来的）。统一成归并口径。
80. **重放时同 `(seq, page0)` 的段删除串代**（g5 seed 36，reopen 后 352 个键 NOTFOUND）：合并产物继承源的最大 seq、
    搬迁保留 seq，B3 又让低位页立刻复用 ⇒ run 6 → 合并进 58 → 搬回 6，新旧两代 `(seq, page0)` **完全相同**；
    清单里老一代的 `M_SEG_DEL` 在重放时把新一代的段摘掉。修法：`apply_man` 处理 `M_RUN_DEL` 时作废该 page0
    的所有待摘段（run 死了，它的段无所谓了；后面新一代的 SEG_DEL 在日志里更晚，不受影响）。
    方法论：这类 bug 只有"随机交错 + 重开 + 逐键比对"抓得到，单元测试永远不会恰好把一条 run 搬回原地。
81. **`write_sb()` 前没有持久化屏障**（g6 seed 1）：数据页 `write` 了但没 `sync` 就写 SB ⇒ SB 落盘、数据页没落 ⇒ 重开
    指向半空的 run。现在 `write_sb()` = `wait_io + sync → 写 SB → sync`，每个持久提交点 2 次 fdatasync。
82. **`shrink()` 同版本重写同一个 SB 槽**（g6 seed 2）：掉电在写到一半 ⇒ 两个槽一个坏一个旧，旧的那个 tail 还是截断前的
    ⇒ 挂载后 `tail_ > 设备长度`。`shrink` 现在也 `++vers_`、换槽写。
83. **槽位 = `vers_ & 1` 被 `commit(false)` 破坏**（g6 seed 3）：逻辑提交也加 `vers_` 但不写 SB ⇒ 连续两次持久提交落到
    同一个槽 ⇒ 掉电把唯一有效的 SB 砸了。槽位改用独立的 `sb_slot_`，每次 SB 写才翻。
84. **截断到了、SB 没到**（g6 seed 4）：`shrink` 先截断设备再写 SB，掉电在两者之间 ⇒ 老 SB 的 tail 超过设备长度 ⇒
    `alloc_pages` 往设备外写（RamDev 报 IO；FileDev 会悄悄把文件撑回去）。挂载时 `dev_pages_ >= tail_` 不成立就按 SB
    把设备截/扩回去。
    g6 本身也踩了一脚：设备"死后"的截断不能改介质镜像（第一版把 `do_truncate` 当成持久，误报）。
    排查掉电失败的顺序：MOUNT 行的 `oa/ob vers` + 上一个掉电点的追踪环 → 哪个 SB 应该活着；`[dev] write FAILED` → 越界写；
    `G6_WATCH=<pid>` 看某页在介质上的变化；`oa=0 vers=977` = 槽读到了但 CRC 无效。
85. **`scrub()` 公开入口不持 `mtx_`**（g7 seed 1 首跑）：单线程无感；并发读者在时 `scrub` 的 `page()`/`ensure_ovfl_loc`
    和读者的 `page()` 互相踢缓存 ⇒ 读者拿到别人的页。同类：`get()` 在锁外取 `open_vers()`、`index_scan` 整个无锁。
    TSan 又抓 3 类：`wait_page` 锁外早退读 `inflight_` 必须 acquire 原子读；`RamDev::np_` 要原子（异步写线程 truncate）；
    `Run::meta_pending` 读写竞争（P1 一起改成三态原子）。教训：**所有公开入口第一行持锁**，`g7`（含 TSan 版）固化。
86. **`std::shared_mutex` 写者饥饿**（g7 `3 6000 4`，4 读者 2 核跑 15 分钟不结束，CPU 198%）：glibc 的 rwlock 默认读者
    优先，读者前赴后继地 `lock_shared`，写者**永远**拿不到；2 读者时碰巧能插进去，4 读者就饿死。`XLock` 自己写：
    有写者在等（`wwait_>0`）新读者退让、自旋 64 次后睡 cv；最后一个读者出门叫醒写者；写者出门 `notify_all`。
    取舍：写者优先意味着写极密时读者吞吐下降；嵌入式存储里"写必须推进"比"读吞吐最大"重要。
    **第二脚**（P5 之后 g7 的写者满负荷）：写者优先 + 读者睡在 cv 上 ⇒ 写者 unlock → notify → 读者醒来要 50 µs，
    写者早又 lock 了 ⇒ 读者 10 s 只做了 **314 次** get。修法"让一手"：写者举牌前若有睡过的读者（`rwait_`）还没拿到
    共享锁，等它们进来（上界 200 µs）。g7 读者 get 314 → 12~19 万（2 读者）/ 85 万（4 读者），写者仍按时完成。
    `make test` 的 g7 段加了 `3 4000 4` 回归。
87. **`rebuild_free()` 把 deferred_/pending_free_ 当空闲页**（P5 放开快照期 shrink 后 g5 seed 1 第 556 步
    `rollback(0)` CORRUPT）：trace 是 `SNAP tail=16 man_last=6` → checkpoint `FREE [6] deferred` → `SHRINK`（里面
    `rebuild_free`）→ `RELOC ALLOC [6] user` —— 快照的清单页被当空闲页发给了新 run，回退点重放到一页数据。
    以前只有 `rollback` 记得在 rebuild 之后 carve 这两张表；`shrink`/`reload` 走到这里就漏。现在 `rebuild_free`
    自己把两张表算作已用（rollback 顺手简化：先决定 deferred_ 再 rebuild）。这也修了一个没被抓到的老洞：快照存活时
    提交失败 → `reload()` → deferred 页流入空闲表。
88. **`count_refs` 是 O(段² × 单元) 而且在 `compact_pass` 里每次提交调两遍**（第 10 轮悬崖的第一层，`gprof` 两处各 19.6 s / 20 s
    墙钟）：`Run::refs` 字段声明了却没人维护，取段集合/释放判定每次都遍历全部单元的全部段去数。单元 1500 × 段 12 时
    每次提交 ~30 ms，5500 单元 × 93 段时 1.5 s。现在 `refs` 由 9 个插/删段落点 O(1) 维护（`attach_run` 新插 `++`、
    `detach_seg`/retire/归并摘段/压实摘段/`M_SPLIT_DEL`/`segdels_` 回放 `--`、`split_pass` 父子同引用 `++`），
    `verify()` 用慢路 `count_refs` 交叉核对（"run refs"）。
89. **压实产物的层号 = `best_lvl + 1`，没有上界**（悬崖的第二层）：`level_pass` 只看 `lvl < LVL_MAX(4)` 的层，
    产物压实两代就到 5/6/7 层，再没有任何合并路径接手；又因为每个单元各产一条私有 run，run 数趋向单元数
    （20k 键 × 500 B × 200 次提交：685 条 run，605 条在 lvl 5；320 次 851 条），每条 run 一张 bloom/元数据，
    get 要逐条探，`compact_pass` 的候选集也跟着膨胀。挂载时把老库的 5/6/7 层夹回 `LVL_MAX`（`apply_man`），
    `verify()` 加 "run lvl" 检查；产物现在进 **L0**（见坑 90）。
90. **压实产物沿用最新源的 seq ⇒ 读到过期值**（修悬崖时 `bench6 ovw` 回读抓到的，**老代码同样有**，
    `ovw 5000 500 200 200` 老引擎 22% 的键回读是旧版本；g5 的工况从来没走到这里）。机制：产物 O 取
    `seq = best_seq`，最新源 F 还活着（别的单元仍引用），O 和 F 同 seq；O 进入一次层合并后，合并产物 M 的
    seq = 组内最大 = F.seq，而 F 不在组内；M 的 rid 若比 F 大，对 F 仍最新的键，M 会以组内老 run 的版本胜出。
    追踪到的实例：cell[0,19) 里 F(rid 116, seq …910, lvl 0) 持 tag 12857，M(rid 312, seq …910, lvl 1) 持 tag 12611，
    `seg_key` 顺序 M > F ⇒ get 返回 12611。修法：**产物保留 `finish_run` 分配的新鲜 seq（全局最大），层号 0**。
    这是名副其实的：单元的段集合覆盖本单元所有键的全部已提交版本（含本单元键的 run 一定被 `attach_run` 挂到本单元，
    直到被某次压实消费），产物里每个版本都是该键此刻最新的；之后刷盘的 run seq 更大、自然压过它。从此不存在
    同 seq 的两条 run，"同 seq 看 rid" 只剩兼容意义。**老库遗留**：升级前就存在的同 seq 对（产物 + 还活着的源）
    在它们被合并掉之前仍可能触发本坑；升级后跑一次 `compact_file()`/`consolidate()` 即清零。
91. **快照钉住的最老 run 让合并组跨过中间 run ⇒ 同样读到过期值**（g8 关掉连续性检查后 3 个种子都在第 18 次提交失败，
    即"第 5 次提交抓快照、第 17 次释放、第 18 次合并"）。`level_pass` 跳过 `ver ≤ snap_max` 的 run，组从它后面开始：
    L0 = [P(9, 钉住), F10..F17] ⇒ 并出 M(17) 到 L1；快照释放后 L0 = [P(9), F18..F25] 并出 M'(25)，
    M' 里 P 的老版本以 seq 25 压过 M(17) 里的新版本。根因是合并的安全条件本来就是**组在全库 seq 顺序上连续**
    （组外不能有 seq 落在组内区间的 run），老代码靠"每层按 seq 取最老 n"隐含保证，快照把它打破了。
    现在显式检查：组在第一个夹缝处截断；若最老那条自己就被隔开，把它**提升**到下一层（只改内存层号，层号只是分组提示，
    不入清单、重开后回到原层也无妨 —— 安全性靠检查而不靠层号），下次它和下一层的老 run 组队。
    教训：**验证正确性的测试必须有逐键模型回读**，`verify()` 只查结构账，查不出"读到旧版本"；g8 每次提交全量比对。

92. **悬空点墓碑把全死的 run 钉住**（第 11 次讨论；老代码同样有）：单元压实把某键整个丢掉（被范围墓碑盖住）之后，老 run 里
    这个键的点墓碑不在任何段里，`exact_live_recs` 整条扫描却把它算活 ⇒ `retire_dead_runs` 把 live 校准成 1，永不退休，
    `verify` 报 `run live recs`。修法：只扫本 run 仍被引用的段的页。
93. **`add_tomb` 同 lo 支配规则删旧墓碑时不看存活快照 ⇒ 快照视图里被删键复活**（老代码同样有）：S0 钉住老 run，A = del_range(100,105)，
    S1，B = del_range(100,110) 支配 A 并删掉它 ⇒ S1 视图（ver 在 A、B 之间）看不到 A，key 100 复活。修法：快照期并存，
    `forget_snapshots` 后 `prune_tombs()`。
94. **点墓碑从不被清除**（老代码同样有）：连全库 `consolidate()` 也把墓碑原样写进产物，写一次/删一次的队列负载库线性增长
    （5 轮 5000→25000 条、36→180 页）。修法见 §10.18：「下面没有更老的物理副本」时丢。
95. **`settle_ranges` 整盖快路径把点墓碑记 0 字节、归并口径算活 ⇒ 快照钉住 run 时 `live mismatch`**。修法：口径统一为
    「赢家就算活」。
96. **坑 94 的第一版按「单元里有没有更老的段」判「更老」⇒ 老值复活**（落地前 g9 t94c 第 30 次提交抓到）：被单元压实摘了段的
    老 run 本体还在，悬空老值随后续层合并进产物、重新挂回单元，墓碑已丢。教训：**「存在更老版本」必须按物理存在判**，
    段只是可见性索引，不是存在性索引。
97. **分步归一的收尾清范围墓碑时没有重写最后那条 run**（落地前 g5 seed 3 抓到）：`consolidate(0)` 是「全部归并一遍再清」，
    分步的最后一步可能一次归并都没做（上一步之后新来了 del_range），清了墓碑 ⇒ `rollback` 后被盖住的键复活。
    不变量：**范围墓碑只能在被盖住的记录物理消失之后清**（现在：收尾步有墓碑就强制重写；归并组恰好是全部 run 时才顺手清）。
98. **`~Store()` 什么都不释放**（第 12 次讨论；新老同在）：`Run` 对象、tls 槽、I/O 线程都靠进程退出收尸，反复 open/close 的进程
    每次 +8 MB；LSan 因此一直是 `detect_leaks=0`。修法：析构 = `wait_io(true)` + 停线程 + `clear_state()`；`detect_leaks=1` 常开。
99. **NOSPACE / abort 路径提前放页**（第 12 轮 L1 落地时）：失败路径里 `promote_pending()` 把本应等下一个超级块的页放回 `free_`，
    下一批 flush 复用它们，老提交点的数据被覆盖。修法：`pend_need_gen_` 闸（只有 `sb_gen_` 真前进到那一代才放）；99b：NOSPACE
    重试再失败必须 `dirty_=true`，NOSPACE 的中间提交点不得持久化 `pend_ranges_`。回归 g11 `t_nospace`。
    同族：类内「抓状态当提交点」的路径（`snapshot()` / `abort()` / `maint_commit()`）必须走 `commit_locked(true)`，不能走公开
    `commit()`——否则 mode 1 下在持锁状态里再跑放锁的维护循环（g5 种子 2 "page owned twice"）。
100. **`split_pass` 每轮 128 刀切不完不吭声**（第 12 轮 M2 验收时）：批量加载（一次提交 50k 条）关库时一堆单元 > BMAX，B1 不变量
    只在下次维护才补齐。修法：`split_pending_` ⇒ `maint_unit` 报 MORE 并在下一单元继续 rebalance。
101. **mode 0 下分步作业每轮 guard 只推进一片**（第 12 轮 M2 验收时）：一次提交 ≤ 16 片，40 片的大合并拖 3 次提交，新 run 堆积到
    1201 条、avg 64 ms。修法：提交点之前（非 one 模式）不开作业、手头作业一口气推完——同一把锁里切片没有意义。
102. **逻辑提交版本是 16 位、没有回绕处理**（第 12 轮全量评估的边界探针 `bench/probe/verswrap.cpp` 发现；v3 从第一天起就有）：
    `xdb::Vers = uint16_t`，每次 `commit(false)` / `commit()` 都 `++vers_`，第 65536 次回到 0。盘上的 SB.vers / 清单 ver / 页头 ver
    全是 32 位，**只有内存里的时钟是 16 位**。后果（70000 次逻辑提交、第 65000 次后持一个快照）：快照视图 2000/2000 个键看见
    "未来"的写（`ver <= view` 对回绕后的小 ver 恒成立）、`verify` 报 `future ver` 2539 处（库其实没坏）、快照钉住所有新 run
    （8 → 29 条）、重开后 `vers_` 跳回 max(run ver)=65281。不持快照时 get/verify/重开碰巧都对（读赢家靠 seq 不靠 ver），
    所以 11 轮测试都没撞到。修法：引擎内版本一律 `u32`（`get_at` 的 view 参数同步放宽；**不是格式变更**），
    "看全部版本"的哨兵从 `0xFFFF` 改成 `~0u`。回归 `tests/g12.cpp`（老头 FAIL / 新头 PASS，≈ 4 s）。
103. **run 序号 `seq` 是 u32、只增不减、没有回绕处理**（同一张边界表的第二项；探针 `bench/probe/seqwrap.cpp` 用 `#define private public`
    把 `next_seq_` 预置到离 2^32 差 50 个号）：回绕后新 run 的 seq 最小 ⇒ 全序里被当成**最老** ⇒ 覆盖写**静默读到旧值**
    （3000 键里 2493 个旧值）、verify `live mismatch`、重开照旧（重开按盘上 seq 重建，回绕后的 run 落进"向下区间"）。
    每次 flush 占一个号（归并产物沿用源的最大 seq，压实产物取新号）⇒ 32 亿次提交：1000 次/s 连续 ≈ 37 天、100 次/s ≈ 1 年。
    本轮只做**响亮失败**：`finish_run` 在 `next_seq_ ≥ 0xFFFFFF00` 时返回 `FULL`（`commit()` 的批次仍在内存、可 `abort`；维护路径不动账），
    探针确认 FULL 之后数据 / verify / 重开全对。彻底修法 = 提交点重编号（全部活 run 按 seq 排序重新从 0x40000000 编号、重写全量清单、
    重建单元段键；**不改格式**，需要无快照、无作业在飞），列为下一轮首项（`backup/r18/swept/docs-hist/EVAL12.md` §6 #1）。
    → 第 13 轮已做：提交点自动重编号（§10.20 ①），`seqwrap 50 400` 回绕 400 次全对。

**评估后没有做的三件**（不是漏掉，是明确判定「现在不值得」）：

| 条目 | 结论 |
|---|---|
| `wait_io` 按批等待 | 现在等待的是「全部在飞页」。但提交是串行的：`commit()` 之前一定先等过前一批，所以「全部在飞」== 「本批」，按批记账不会改变任何一次等待的长度，只会多出一种「批内部分完成」的失败态。真正需要的按页等待 `wait_page(pid)` 早就有了。**不做**，避免为了语义漂亮引入新的挂起面。 |
| `compact_file` 单遍化 | 现在的两遍是**故意的**：第一遍归一之后旧段还占着低位，合并出的 run 只能落在高处；第二遍低位全空了才能整块搬到最前。单遍化要先算好每个单元的最终落点，等于把「run 跨单元」这个模型改成「按单元预分配区间」——那是换架构，不是优化。实测 1500 页 / 4 万条活数据的 `compact_file` 是 **24 ms**（回收 1192 页），不在瓶颈上。 |
| `alloc_pages` size-class 桶 | 首适配是 O(空闲块数)，而长跑里空闲块数实测 **≤5**（`s2` 末态 2 块）。size-class 索引要在 6 个改 `free_` 的地方同步维护，收益是省几十次 map 迭代。**不做**。 |
| 读路径页 CRC | 页 CRC 只在 `verify()` 里校验。读路径每页多一次 CRC32C 是 ~7.5 GB/s 的吞吐（SSE4.2），对 4 KB 页等于 0.5 µs —— 点查的总量级才 0.3 µs，翻倍都不止。做法留给 `scrub`（后台慢扫），这一轮不改读路径。 |

## 14. 还能往哪走（按性价比）

> **产品主树 = R17 定稿**（2026-10-20 battle 升格）。峰值现状与否定结论见 §13.16 / `docs/00-entry/EVAL17.md`；本机「小预留 TRIM 关」分叉仅归档（`docs/00-entry/BATTLE.md`）。

0. **再压合并峰值（R17 之后）**：养洞 / L1 吃大洞（§13.16、ROUND17 §2.5）——P2c 稀疏 run，或 `alloc_pages` 策略让新 L1 不吞合并洞；**不要**再拧 cliff/dirty 旋钮（A/B 已否定）。
1. **页大小自适应**：现在页固定 4 KB。OLTP 小值场景 1~2 KB 页能少一半，扫描型负载
   8~16 KB 页能少一半页头/CRC 开销。要动的是 `PAGE` 作为编译期常量的所有落点。
2. **值压缩**：引擎对值是不透明的，压不动也不该压；真需要压就在应用层放（或做一层
   "压缩值编解码器"挂在 `put/get` 外面，不动存储格式）。
3. ~~**局部 TRIM**~~ **已做（第 11 轮 R8）**：`BlockDev::discard(pid, n)` + `FileDev` 的 `fallocate(PUNCH_HOLE | KEEP_SIZE)`，
   `set_discard_min_pages(m)` 打开后只对 `promote_pending` 里回到 `free_` 的 ≥ m 页整段打洞（§10.18）。
4. **把 `flush_mem` 移出写锁**（= R3，设计稿 `backup/r18/swept/docs-hist/DISCUSS12_R3.md`，第 11 轮只出设计）：现在多写者只有 1.4~1.5×，瓶颈是 `flush_mem`（O(内存表)
   遍历）和 `commit_delta`（清单页 + SB）都在锁里。做法是把 RunWriter 的"写页"阶段拆出去
   （`free_`/`tail_` 的分配仍加锁，页写完成后再回来挂 run）。收益预计 2.5~3×。
5. ~~**溢出链共享 + 引用计数**~~ **已不需要**（第 7 轮）：压实早已"接管"链不复制（§10.13），
   `compact_file` 变大的根因是链不动而不是链被共享；用 `take_limit_` 物化高位链就把 +31% 压到 +0.8%
   （§12 坑 61）。多 run 共享一条链仍然不允许（源 run 必死），格式没升版。
   还剩的真问题是 **M2：把 run 的页写移出 `mtx_`**（`rget` 4 线程负扩展、多写者 1.4×）。
6. ~~**范围墓碑的自动归一**~~ **已做（第 11 轮 R7）**：`set_range_tomb_auto(n)`，墓碑 ≥ n 且无快照时每次提交后多做一步
   分步归一直到清空（§10.18；默认关）。
7. **`scrub` 的结果落地**：现在只报告。单副本没有冗余可修，但可以把坏页的**键范围**
   报出来，让应用层决定重建哪些数据；有副本时（将来的 2 副本模式）可以直接从对端修。
8. **把存活账也持久化**：每次提交为变化的 run 追加一条 `M_RUN_LIVE`（40 B），再给 `Seg`
   记一份 `(run, 上次落账的 live)`。做成之后挂载就彻底 O(runs)，`recompute_liveness`
   只在 `verify()` 里跑。难点是「段拆分/合并时怎么对齐这个增量」，以及和快照的交互 ——
   所以这一轮只把坑写清楚，不动手。
9. **元数据页瘦身**：bloom（2 B/记录）和 sp（1.25 B/记录）占了 meta 的 95%。两条路：
   bloom 用 8 bit/键换 1 B（误判 0.24% → 3%，读路径会多读页，不划算）；
   sp 改成「按页惰性重建」（每次只解码被访问的那一页，最多 200 条）——这条能把写放大
   压回去 0.14×，值得下一轮做。

### 14.1 第 12 轮全量评估之后的优先级（`backup/r18/swept/docs-hist/EVAL12.md` §6；按"必撞 / 静默"排序，不按工期）
