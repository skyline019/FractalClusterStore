# P2 设计稿：格式 v2（全量档）—— seq/ver 64 位 + `M_RUN_TRIM` 分片归并 + 稀疏 run + 老库自动升级

> 状态：**第 16 轮已实施 P2a + P2b**（§9 六项全按建议值拍板；P2c 稀疏 run 只预留了 `M_RUN_HOLE = 8`）。实测与差异在 `docs/20-rounds/ROUND16.md`，与本稿不同的四处：
> ① §4.2 "open 内立即升级" ⇒ 实现为**惰性升级**（第一次写 SB 即 v2；只读不升不需要新参数）；② §3.2 "P = max(1024, 产物/64)" ⇒ 实现为片大小**上限**，
> 另有下限 max(64, 产物/64)，每片按当前最大的洞挑大小，产物 < 1024 页不分片（固定 1024 片实测零收益，见 ROUND16 §4.2）；③ 切点在单元边界 ⇒ 一个单元只落一片
> （本稿允许两段）；④ 本稿的峰值 [预估]（bench4 200k ≈1.45×、layout 800k ≈1.15×）**未达**：实测 1.94× / 1.40×，差距来源量在 ROUND16 §4.1/4.2。
> 下文保持设计稿原貌。所有数字里标 [实测] 的来自 ROUND14/15 的探针，标 [预估] 的是推算。

## 0. 为什么要升版、为什么要一起上

| 痛点 | 现状 [实测] | 现格式能不能治 | v2 的解法 |
|---|---|---|---|
| **顶层合并峰值 2×** | layout 200k 峰值 2.60×、800k 1.56×、bench4 200k 2.44×（ROUND14 §1.2.0；第 15 轮二步搬家只治合并**后**的静态占用，1.97× → 1.40×，不治峰值） | 不能：产物是一整条 run，源要等产物整条落地才能释放；总空闲 < 产物时谁也并不出洞 | **分片归并 + 源 run 前缀 trim**（`M_RUN_TRIM`）：产物每落一片（一条独立的小 run）就把源已归并完的前缀释放 ⇒ 峰值 ≈ 活 + 一片 |
| seq / ver 32 位回绕 | 坑 102（ver）、坑 103（seq：第 13 轮用提交点重编号 `renumber_seqs_locked` 兜住，≈10.7 亿次 flush 一次；前提多：无快照、无作业、本批无范围墓碑） | 只能兜，不能根治 | 清单项 ver/seq 加宽到 64 位，重编号与回绕处理退役 |
| 单元压实后死页收不回 | 压实把一个单元的段重写成小 run，源 run 里该单元的页成了死页，要等整条 run 全死（`retire_dead_runs`）或被层合并才释放（R0 悬崖时代的"文件只涨"根源之一） | 不能：run 的页区间是连续块，没有"中间挖洞"的持久表示 | **稀疏 run**：`M_RUN_HOLE` 记录 run 内部已释放的页区间 |
| 老库 | `tests/golden/*.img` 三个 v1 镜像（H2） | — | 挂载识别 v1 → 一次全量清单重写升到 v2；老代码遇 v2 清楚地拒绝 |

一起上的理由：格式升版的固定成本（SB 魔数/版本号、golden 重生成、升级路径、兼容测试）只付一次；三项都要改清单项（ManEnt）和挂载重放（`apply_man` / `attach_run` / `rebuild_free` / `verify`）。
**不**一起上的（可选搭车，§7）：R4 内联上限、R5 sp 惰性、R6 `M_RUN_LIVE`、小记录头。

## 1. 现格式的事实（改动基线，fcs.h 第 14/15 轮头）

- 超级块 `Sb`（L3550）：`magic=PK_SB('FCSB') vers state chk tail man_first man_last nman n_inl pad`，10 × u32 = 40 B（`SB_HDR`），其后内联 ≤ 32 条增量；双槽交替，CRC 覆盖头 + 内联。`pad` 没人读（DISCUSS10 §6 早就圈它做版本号）。
- 清单项 `ManEnt`（L2922）40 B：`op(1) lvl(1) [2 空] ver(4) key(8) last(8) page0(4) npages(4) nbytes(4) seq(4)`；`MAN_PER_PG = 102`。op：`M_RUN_ADD/DEL, M_SPLIT_ADD/DEL, M_SEG_DEL, M_RANGE`。
- run 的身份 **rid = page0**（`seg_key(seq, rid)` 是单元段表的键，L478；`runs_` 按 page0 索引）。搬家（relocate / 第 14、15 轮的回收策略）= 同 seq 同 ver 换 page0。
- run 元数据页 `PK_RMETA`（56 B 头：magic2 page0 npages nrec nbytes nsp nkid bwords bits first last）和数据页头 `DHDR=40` **不含 seq/ver**（版本是 run 的属性，只在清单里）⇒ 64 位化**只改清单与 SB**，数据页零改动。
- 段表是**派生量**：挂载时 `attach_run` 按 run 的 `[first,last]` 与 fences 给每个单元建段（L3261）；只有"单元压实后不再引用某条活 run"这种例外才持久化（`M_SEG_DEL`）。
- 空闲表也是派生量：`rebuild_free` 按"所有 run 的块 + 清单页 + 溢出链"的补集重建。

## 2. v2 格式规格

### 2.1 超级块

```
v2 Sb（48 B）：magic=PK_SB2('FCS2')  fmt=2  state  chk  tail  man_first  man_last  nman  n_inl  vers_lo  vers_hi  reserved
```
- 换魔数而不是只改 `pad`：老代码读到 `'FCS2'` 直接"magic 对不上 → 两槽都无效 → CORRUPT"，**干净拒绝**；若沿用老魔数，老代码会按 40 B 解析 48 B 的内联项，靠 CRC 不匹配才拒绝——结果一样但路径不干净。
- `read_sb` 先看魔数：`PK_SB` ⇒ v1 解码（只在升级路径用）；`PK_SB2` ⇒ v2；其它 ⇒ 无效槽。
- `INLINE_MAX`：v2 项 48 B，`(4096 − 48) / 48 = 84` ⇒ 顺手把 32 提到 **80**（R4 的一半收益，零成本；见 §7）。

### 2.2 清单项（48 B）

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | `op` u8 | 原有 6 个 + `M_RUN_TRIM = 7`、`M_RUN_HOLE = 8` |
| 1 | `lvl` u8 | 不变 |
| 2 | `flags` u16 | 预留（位 0：本条属于"分片家族"，见 §3.3） |
| 4 | `page0` u32 | rid |
| 8 | `key` u64 | ADD：首键；TRIM：**trim 后的首键**；HOLE：洞起始页偏移（run 内） |
| 16 | `last` u64 | ADD：末键；HOLE：洞页数 |
| 24 | `npages` u32 | ADD：页数；TRIM：**新的起始页偏移**（run 内，≥ 1，见 2.4） |
| 28 | `nbytes` u32 | ADD：字节数；TRIM/HOLE：释放掉的有效字节（存活账用，可为 0 = 让挂载按 pcum 算） |
| 32 | `ver` **u64** | |
| 40 | `seq` **u64** | |

`MAN_PER_PG = (4096 − MHDR 16) / 48 = 85`。清单页头 `MHDR` 不变。

### 2.3 内存侧 64 位化

- `Run::ver/seq`、`vers_`、`next_seq_`、`snaps_[].vers`、`ManEnt::ver/seq`、`Sb.vers` → u64；`open_vers()` 返回 u64；公开 API 里暴露版本号的（`snap_version`、`get_at(view)`）改签名（**源码级不兼容**，调用方重编译即可）。
- `seg_key(seq, rid)`：64+32 位装不进 u64 ⇒ `struct SegKey { u64 seq; u32 rid; }` + `operator<`，`SegMap = std::map<SegKey, Seg>`。`rbegin()`="最新段"的语义不变。map 节点 +8 B。
- 退役：`renumber_seqs_locked`、`seq_renum_at_`、`SEQ_EXHAUSTED`、`seq_headroom()`、坑 102 的 ver 回绕处理（保留测试段改成"64 位不回绕"的断言）。
- 合并赢家 / 层分组 / 坑 94 的连续前缀检查：比较 u64，逻辑一字不变。

### 2.4 `M_RUN_TRIM`（源 run 前缀释放）

语义：run `rid` 的页 `[page0 + 1, page0 + npages_trim)` 已释放，run 的逻辑首键变成 `key`，`[page0 + npages_trim, 块末)` 原样有效。
- **第 0 页永远不释放**（身份锚）：rid = page0 是全局身份；若把 page0 释放再被新 run 分到同一地址，`runs_` 就有两条同 rid 的 run。留一页（4 KB / 条被 trim 的源 run，源 run 最终 DEL 时一起还）比换身份（要把所有单元的段表重键，等于一次 relocate 的簿记）便宜得多。
- 内存：`Run::trim`（run 内页偏移，单调不减）。`attach_run` 的栅栏指针从 `pi = trim` 起、`first = key`；`run_block()` / `rebuild_free` / `verify` 的 owned 集 = `{page0} ∪ [page0+trim, 块末)`；`live_bytes/nbytes` 按 `pcum` 扣；bloom / sp 不动（被 trim 的键再也没有单元引用这条 run，探测到不了）。
- 重放：`apply_man` 遇 TRIM 取 `max(trim, npages)`；TRIM 必须在同一提交点里**晚于**覆盖这些键的 ADD（§3.2 的顺序保证）。
- 释放纪律同今天：进 `pending_free_`（提交点之后可复用）；快照钉住（`ver ≤ snap_max`）⇒ `deferred_`（P5：快照存活期间峰值收益不成立，明说）。
- 不需要逐单元的 `M_SEG_DEL`：段表是派生量，`first = key` 就够（ROUND14 §5.1 的两个选项里选"trim 记录带键界"）。

### 2.5 `M_RUN_HOLE`（稀疏 run）

语义：run `rid` 的页 `[page0 + key, page0 + key + last)` 已释放（run 内偏移）。
- 来源：单元压实（`compact_cell`）之后，源 run 在该单元键域内**整页落在单元内部**的页（首尾两页可能与邻单元共享，留着）；以及未来任何"一段键域不再引用这条 run"的场合。
- 内存：`Run::holes`（有序、不重叠的区间表，合并相邻）；owned 集扣掉洞；`run_block()` 退化为"连续块"的概念不再成立 ⇒ 搬家 / 二步搬家规划器 / `relocate()` 按 **owned 区间**算（洞就是普通空闲页，可被别的 run 占用）；扫描游标永远在段的 `[p0,p1)` 内走，而洞只由整段死掉的页构成 ⇒ 游标不会踩进洞；B2 预读窗口（8 页）要**按 owned 区间截断**（这是最容易漏的一处，坑 67 同款：预取绕过所有逻辑直接读页）。
- 重放：区间并集；与 TRIM 的交互：`trim` 之下的洞直接丢弃。
- 与现有 `M_SEG_DEL` 的关系：SEG_DEL 说"这个单元不再引用这条 run"，HOLE 说"这些页已经还了"；压实时两条一起写，HOLE 只覆盖能整页释放的部分。

### 2.6 数据页 / 元数据页 / 溢出页

零改动（§1 第 4 条）。`PK_RMETA` 的 `page0` 字段仍是 rid。

## 3. 分片归并协议（峰值的真正修法）

### 3.1 现状
一次层合并 = 一个作业（`start_job` / `merge_job_step`），产物是**一条** run，流式预留一整块（第 14 轮按存活字节估 + 就地续租），`finish_run` 之后在下一个提交点 `M_RUN_ADD(产物) + M_RUN_DEL(源…)`；源块在那之后才进 `pending_free_`。峰值 = 活 + 产物 ≈ 2×。

### 3.2 v2：产物按片独立成 run，每片一个提交点

```
作业开始：源集合 S（同今天），分片上限 P 页（set_merge_part_pages，默认 1024 = 4 MB；0 = 老行为）
循环：
  归并直到产物写满 P 页（或源耗尽）⇒ finish_run(片 i)：独立的 run（自己的 RMETA / bloom / sp），lvl = 目标层，
     seq = 作业 seq_base + i（见 3.3），键域 [k_i, k_{i+1})
  在**下一个提交点**（maint 产物本来就是下一个 SB 入账）写入：
     M_RUN_ADD(片 i)
     对每个源 r：M_RUN_TRIM(r, npages = 游标 cur.p0（该源第一个仍含 ≥ k_{i+1} 键的页），key = 该页首键)   ← 晚于 ADD
  提交点落盘 ⇒ 源的已归并前缀进 pending_free_ ⇒ 下一个提交点可复用
源耗尽：最后一片 ADD + 所有源 M_RUN_DEL（同今天）
```
- 峰值 = 活 + **一片**（P）+ 在飞的 pending（最多一个提交点的量）[预估]：bench4 200k（活 9 MB）2.44× → ≈ 1.45×；layout 800k 1.56× → ≈ 1.15×；layout 200k 2.60× → ≈ 1.5×。
- 写量不变（每字节仍只写一次）；清单多：每片 1 条 ADD + 每源 1 条 TRIM（10 个源 × 20 片 = 200 条，几页清单）。
- 读路径：一个单元仍只落在一片里（片按键域切、单元按键域切，二者都是区间 ⇒ 每单元对产物最多两个段：跨片边界的单元各引用两片的相邻段）。段数上界 `SMAX` 不变。bloom 按片建（更小、误判率同）。
- 崩溃 / 中断：每个提交点都是自洽状态——片 1..i 已入账、源已 trim 到 k_{i+1}。作业状态不持久化（同今天）：重启后源就是"首键 = k_{i+1} 的短 run"，层合并规则自然把它们再挑出来接着合（**不必续作业**）。
- 流式预留：每片只预留 ≤ P 页（按存活估、就地续租规则不变）⇒ 预留本身也不再撑文件。
- 单元级增量账（第 14 轮 job_fast 公式）：按片收尾一次，公式里的"源段区间"变成"源的 [trim_old, trim_new)"，仍是一次性可算的量。

### 3.3 片的 seq 与层规则
- 今天产物取"组内最大 seq"（相对顺序不变）。分片后：片 i 取 `seq_base + i`，`seq_base` = 组内最大 seq。片之间键域不交 ⇒ 顺序无所谓；与**被 trim 的源**同 seq（片 0）但键域不交 ⇒ 赢家判定不冲突（同键永远不会同时出现在源和片里）。
- 坑 90 / 坑 94 的"同 seq 对"与"连续前缀"检查：家族（同一次作业的片）在 `flags` 位 0 标记，层分组把一个家族当**一条**计数（否则 20 片把 `lvl_t` 顶满、触发无意义的再合并）。这是本设计最需要在实现时对着 `level_pass` 逐条规则核的地方。
- 搬家 / 回收策略：片是普通 run，照搬；trim 过的源：owned 区间 = 锚页 + 尾部，规划器按区间算。

### 3.4 替代方案（为什么不选）
- **顶层按键区常驻分区**（LSM 的 SST 式）：顶层永远是 N 条键域不交的 run，合并只碰相交的分区。峰值同样 ≈ 一片，但要改层结构与合并选择（按分区挑源），改动面远大于 3.2；而 3.2 只改"产物怎么切、源怎么收"，层规则不动。先做 3.2；若将来顶层很大（几十 GB）再考虑常驻分区，二者不冲突（3.2 的片就是分区的雏形）。
- **产物就地可见（部分 run）**：片未写完先让读者读 ——需要"生长中的 run"的清单表示和 sp/bloom 的增量构建，否决。

## 4. 老库升级路径

1. `open()`：读两槽，按魔数分流。`PK_SB`（v1）⇒ v1 解码器读 SB 内联 + 清单链（40 B 项），建内存状态（字段加宽零损失）。
2. 可写挂载：**open 内立即**写一份 v2 全量清单 + v2 SB（与 `checkpoint` / 第 13 轮 `renumber` 同一条路：O(runs) 条、几页、2 次 fsync），然后才返回。崩溃在 v2 SB 之前 ⇒ 下次挂载仍是 v1，再升一次（幂等）；之后 ⇒ v2。另一槽的 v1 SB 在下一次提交被覆盖。
3. 只读挂载（`open(..., read_only=true)`，新参数）：不升级、不写；golden 测试与"先看看再决定"的运维场景用。
4. 老代码（第 15 轮头）打开 v2 库：魔数不对 ⇒ 两槽无效 ⇒ `CORRUPT`，`Report.first_err = "format"`（加一个明确的字符串；不另加 RC 值，避免调用方 switch 漏项）。
5. 升级后不需要额外的 `compact_file()`：全量清单重写就是一次"按内存状态规范化"（坑 89 的夹层号、坑 90 的同 seq 对都已在内存里收敛）。可选跑一次 `verify()` 作为运维确认。
6. 版本号只认 1 和 2；`fmt > 2` 拒绝（前向：新库不让老代码碰）。

## 5. 风险（按我现在能看到的排序）

1. **分片与层规则的交互**（§3.3）：家族计数、连续前缀、脏度分组（规则 (a)/(d) 按 run 的 live_bytes 算，trim 后要用扣减后的值）。最可能出坑的地方；g8（R0 悬崖）/ g13 / g14 jobacct 全套要跑。
2. **预读窗口踩洞**（§2.5）：坑 67 同款。稀疏 run 单独一段白盒测试：在洞里放别的 run 的页，预读不许读到。
3. **`rebuild_free` / `verify` 的 owned 集**：三种新形态（锚页、trim 尾、洞）都要进"page owned twice / unowned"检查；g5 随机掉电 + h1 挂载模糊覆盖。
4. **快照期间 trim 全部进 `deferred_`**：长快照下峰值回到 2×（P5 规则）。文档明说，不另做机制。
5. **源码级 API 变更**（u64 版本号）：调用方重编译；`get_at(view)` 的 view 类型变了。
6. **升级不可逆**：可写挂载即升级；提供只读挂载给"先看看"。
7. **64 位化本身**：机械改动量大（seq/ver 出现 300+ 处），靠编译器 + `-Wconversion` 过一遍，靠 golden + 全回归兜底；坑 102/103 的测试段改成断言"越过 2^32 不回绕"（白盒把 `vers_` / `next_seq_` 预置到 2^32 − 5 再写 10 次提交、重开）。

| g16 snap | 快照存活期间 trim 进 deferred；释放后回收 | 文件在快照期不落、释放后回落 |
| g16 wrap | vers_/next_seq_ 预置到 2^32−5 越过；无重编号路径 | 顺序正确、重开正确 |
| 峰值 [实测] | `layout 200k/800k`、`bench4 200k`、新加"峰值"列 `peak_tail` | 峰值 ≤ 活 + P + 一个提交点的 pending（断言写进 g16 part） |
| 全量 | 46 段 + asan/TSan | 全绿 |

## 7. 搭车项（可选，建议只带第一项）

| 项 | 成本 | 建议 |
|---|---|---|
| R4 内联上限 32 → 80（§2.1 顺手） | 0 | 带 |
| R5 sp 惰性重建（meta 95% 是 bloom + sp） | 中：改 RMETA 页布局 ⇒ 数据侧也动 | **不带**：让 v2 保持"数据页零改动"，升级才能是 O(runs) |
| R6 `M_RUN_LIVE` 存活账持久化 | 低：新 op | 不带：10 M 条以上才有感，且第 12 轮 R6-lite 惰性账已经把挂载摊开了 |
| 小记录头（10 B → 更小） | 高：数据页格式 | 不带 |

## 8. 工期与分段（预估）

| 段 | 内容 | 工期 | 验收 |
|---|---|---|---|
| P2a | 魔数/版本号、48 B 清单项、64 位化、升级路径、只读挂载、golden v2 + v1 升级测试、重编号退役 | 2 天 | 46 段 + g16 fmt/upgrade/wrap + asan |
| P2b | `M_RUN_TRIM` + 分片归并 + 家族计数 + 峰值断言 + 崩溃点 | 3~4 天 | g16 trim/part-crash/snap + 峰值实测三组 |
| P2c | `M_RUN_HOLE` 稀疏 run + 预读截断 + 压实接入 | 2 天 | g16 hole + f5（空间回收）回归 |

P2a 单独就能发（它本身只是"更宽 + 可升级"）；P2b 是峰值的收益所在；P2c 收益最小、风险在预读。建议顺序 a → b → c，**每段都跑全量 test + asan**，三段放一轮还是两轮由用户定。

## 9. 请审的问题

1. 分片协议选 §3.2（产物切片 + 源 trim）而不是常驻分区（§3.4），同意？
2. 锚页方案（trim 永远留第 0 页，4 KB/源 run）vs 换身份（rid 变更要重键段表）——建议锚页。
3. 稀疏 run（P2c）要不要这轮一起上？它和峰值无关，收益是压实后的死页；若砍掉，`M_RUN_HOLE` 的 op 号先预留。
4. 升级策略：可写挂载即升级（不可逆）+ 只读挂载不升级，同意？要不要一个 `FCS_REFUSE_UPGRADE` 编译宏给保守部署？
5. 搭车项只带 R4，同意？
6. 默认分片 P = 1024 页（4 MB）：小库峰值 +4 MB、大库片数 = 产物/4 MB（10 GB 顶层 ⇒ 2500 片 ⇒ 清单 2500 条、每片一个 RMETA）。要不要按产物大小自适应（`max(1024, 产物/64)`）？
