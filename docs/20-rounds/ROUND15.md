## 1. ③ 二步搬家：问题、做法、坑

### 1.1 第 14 轮留下的问题
`set_hw_reclaim_pct(pct)`（默认 0 = 关）：`tail_ > 活页 × pct/100` 时，维护空闲把**最顶上的 run** 搬进一个放得下它的低洞。第 14 轮的实测是它常常**停在半路**：bench4 200k pct=150 末态 1.97×、hwmap pct=130 2.40×——顶上的 run 比任何单个洞都大，而洞总量其实够。原因是洞被几条小 run 隔开（"挡路 run"），单步策略只会"找一个放得下的洞"，找不到就放弃。

### 1.2 做法（`hw_reclaim_pass` 二步版）
1. **一步**（不变）：顶 run 能整条放进某个低洞 ⇒ 搬。
2. **规划**（新，`hw2_plan`）：找不到洞时，在 `tail_` 以下按地址扫一遍"洞 / run"序列，找一个**窗口**（连续地址区间）满足 Σ洞 + Σ窗内 run 的块 ≥ 顶 run 需要的页数，窗内 run 全部能在**窗外**找到落地的洞（`hole_below`，排除窗口本身），且窗口的"代价"（要搬的页数）最小。
3. **搬挡路 run**（`hw_move_run`，每个提交点一条）：把窗内 run 搬到窗外（小的当场重写，大的走单源作业，同一步搬家的路径）；搬完窗口并成一个大洞 ⇒ 下一个提交点一步搬顶 run。
4. **回避窗**：规划期间 `alloc_pages` 跳过窗口地址（`avoid_lo_/hi_`），否则 flush/合并产物会立刻把刚腾出来的洞占掉。
5. 账：`MaintStats.hw_blockers`（搬了几条挡路 run）、`hw_reclaims`（顶 run 搬了几次）。

### 1.3 坑（按发现顺序，含否掉的）
| # | 坑 | 处理 |
|---|---|---|
| 1 | 同一提交点里规划两次会**换窗交替**（两条候选窗代价相同，先后搬了 6 条挡路 run 才并出洞） | `hw2_gen_`：一个 SB 代数只搬一条挡路 run |
| 2 | `hw2_gen_` 在规划**前**记 ⇒ 规划失败（没有窗外目的地 / 快照钉住）后，后面的**空提交**（SB 代数不涨）把策略永久闸死——g15 的"快照钉住"段抓出来的真 bug | 只在成功发起搬家后记；搬失败归零（修正 3） |
| 3 | 规划器用 `tail_` 做顶界，而顶部刚释放的 run 页还在 `pending_free_`（下个提交点才回落）⇒ 规划把"将要消失的顶"算进代价 | `hw_eff_tail()`：顶部贴着 pending 的区间不算 |
| 4 | **否掉**：「顶 run 之上压着清单页就跳过」（怕白搬：清单页不走 tail_ 不回落）。实测 layout 200k pct=150 从 1.35× 变成 **2.49×**——清单页在顶部是常态且短命，这个 guard 改变了整条轨迹（末态 L2 289 页卡在两洞之间没有窗外目的地）。不加 guard 时清单页走后 tail_ 自然回落，搬下去的都不白搬；多余搬家只在"阈值永远达不到"时发生且有上界（顶部严格下降、每个顶的挡路 run 有限） | 删除，原处留注释 |
| 5 | 轨迹对策略细节**高度敏感**（混沌）：一个 guard 能把末态从 1.35× 变 2.49×；pct 110/130/150/170 的末态不单调 | 判据改为**看矩阵**（4 个 pct × 3 个负载）而不是单个数字；本轮矩阵每格都 ≤ 老头 |
| 6 | 白盒搭布局：1 页小 run 不是墙（会被当挡路 run 搬走）；相邻释放的填充块会并成洞改变最便宜窗；清单页簇落在顶 run 之上让 `tail_` 不回落；快照存活期间 `free_pages` 进 `deferred_` 不成洞；搬家后旧 Run 对象销毁只能按 seq 找；verify 把永久填充块报 unowned | g15 用 4 页**永久填充块**当墙；断言用 `runs_top`（max(page0 + 块长)）不用 `tail_`；收尾先 `free_pages` 再 commit 再 verify |
| 7 | 规划器 O(n²)（n = 顶以下的洞 + run），持锁 | n 几百量级时几十 µs；上界 n²·常数，1000 项 ≈ 1 ms；只在"顶 run 装不下任何洞"时跑一次/提交点。接受，记在这里 |

## 3. ② fsync 出锁 —— 讨论稿摘要（全文 `docs/30-discuss/DISCUSS15_FSYNC.md`）
- 关键发现：`get()` 以 `open_vers() = vers_+1` 读、先查 `mem_` ⇒ **未提交的 put 对所有读者本来就可见**，"可见先于持久"是现状而非新语义；ROUND14 把出锁写成语义变更，要收回一半：读者可见性模型不变，不需要"读者视图版本门"。
- 真正要改的两道内部纪律：页复用闸的代数拆成 `sb_built_`（锁内抓载荷）/ `sb_synced_`（锁外同步完）——否则 mode 3 在飞行中 SB 期间释放的页会被错误放行（坑 99/104 同款）；SB 顺序用提交顺序器串行，失败 ⇒ `dirty_` 重建。
- 方案 = 提交三段：锁内（flush_mem 发写 + 清单内存 + 抓 SB 载荷）/ 锁外（wait_io + sync + SB + sync）/ 锁内 µs 级（发布代数、`promote_pending`）。持锁调用方（`maint_commit`、renumber、NOSPACE 中间提交点）走内联版。
- **分解实测**（`FCS_PROF=1`，空机）：本沙箱一次 fsync p50 0.25 ms；提交锁内 ≈2~3.5 ms，其中 `flush_mem`（编码 + 发写）avg 0.8~1.5 / max 2.6 ms 是大头，`commit_delta`（含 2 次 fsync）avg 0.4~0.8 / max 1.0~5.5 ms；stall mode 1 读者 max 3.5 ms（ROUND14 的 5.7 ms 是与其它负载并行时量的）。**修正 ROUND14**：「地板 = 两次 fsync」没分解就下结论，本沙箱 fsync 只占 1/4~1/3。
- 预估：只搬 fsync ⇒ 本沙箱读者 max 3.5 → ≈2.5 ms；慢盘（fsync 1~30 ms）收益 = 2 × 设备延迟；要亚毫秒得连 `flush_mem` 也出锁（双内存表，§3.5，改动大一圈）。提交者延迟不变；组提交后话。
- 代价：失败窗口变宽（内存已切换、盘未落、`dirty_` 重建）；mode 0 不受益；2~3 天 + 1 天测试。待拍板 5 问（§7）。

## 4. ① P2 设计稿摘要（全文 `docs/10-design/P2_DESIGN.md`）
- v2 = 新魔数 `'FCS2'` + 48 B SB 头 + 48 B 清单项（ver/seq u64、`M_RUN_TRIM=7`、`M_RUN_HOLE=8`）；数据页 / RMETA / 溢出页**零改动** ⇒ 升级是 O(runs) 的一次全量清单重写。
- 峰值修法 = **分片归并**：产物每 P 页（默认 1024）独立成 run、下个提交点 `ADD 片 + 每源一条 TRIM`；源的已归并前缀立刻进 `pending_free_`；崩溃不必续作业。峰值 ≈ 活 + 一片 [预估：bench4 200k 2.44× → ≈1.45×，800k 1.56× → ≈1.15×]。
- TRIM 永远留第 0 页做身份锚（rid = page0）；段表是派生量 ⇒ TRIM 带键界即可，不需要逐单元 `M_SEG_DEL`。
- 稀疏 run（R0）此前只有名字，本稿给了定义：`M_RUN_HOLE` 记 run 内部释放的页区间，来源是单元压实；最大风险是预读窗口踩洞（坑 67 同款）。
- 升级：可写挂载即升级（幂等、不可逆）、只读挂载不升级、老代码遇 v2 干净拒绝；v1 golden 保留作升级输入。
- 分段 P2a（格式 + 64 位 + 升级，2 天）/ P2b（TRIM + 分片，3~4 天）/ P2c（稀疏 run，2 天）；待审 6 问（§9）。
